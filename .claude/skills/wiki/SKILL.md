# Wiki

Maintain the persistent knowledge base in `docs/wiki/`. The wiki compounds over time — knowledge is compiled once and kept current, not re-derived every session.

## Structure

```
docs/wiki/
  index.md              — catalog of all pages with one-line summaries
  log.md                — append-only chronological activity log
  _templates/           — page templates
  experiments/          — experiment findings (auto-generated by /reporter)
  methods/              — architecture decisions, design rationale
  meetings/             — supervisor meeting notes, decisions, action items
  research/             — paper summaries, related work insights
```

## Operations

### Ingest

Process new knowledge and integrate it into the wiki. Triggered by:
- User shares meeting notes, paper insights, or design decisions
- `/reporter` creates an experiment page (reporter writes directly, not through this skill)

Process:
1. Read the source material
2. Determine which wiki category it belongs to (`experiments/`, `methods/`, `meetings/`, `research/`)
3. Create or update the relevant wiki page(s) using the appropriate template
4. Update cross-references — add `## Related` links to/from existing pages
5. Update `index.md` — add or update the entry under the correct category
6. Append to `log.md`

### Query

Search the wiki to answer a question.

Process:
1. Read `index.md` to find relevant pages
2. Read the relevant pages
3. Synthesize an answer with citations to specific wiki pages
4. If the answer is valuable and novel, offer to save it as a new wiki page

### Lint

Health-check the wiki for quality issues.

Check for:
- **Contradictions** — pages that disagree with each other
- **Stale claims** — findings that newer experiments have superseded
- **Orphan pages** — pages with no inbound links from other pages
- **Missing pages** — concepts referenced in `## Related` that don't have their own page
- **Missing cross-references** — pages that should link to each other but don't
- **Empty categories** — wiki categories with no pages yet

Report findings and offer to fix them.

## Templates

### Experiment page (used by /reporter)

```markdown
# <Experiment Name>

**Status**: running | completed | failed | superseded
**Date**: YYYY-MM-DD
**Tags**: #tag1 #tag2
**Wandb**: <run URL>
**SLURM Job ID**: <job id>
**Slides**: <link to HTML slide deck>

## Setup

What was tested and why. Hypothesis in one sentence.

## Changes

What changed compared to the previous run.

## Results

Key metrics, embedded plots via ![](../../output/figures/...).

## Findings

What we learned. What surprised us. What this means for the research question.

## Next

What to try next based on these results.
```

### Generic page (meetings, methods, research)

```markdown
# <Title>

**Tags**: #tag1 #tag2
**Date**: YYYY-MM-DD

---

<Content>

## Related

- [[other-page]]
```

## Conventions

### index.md format

One entry per page, organized by category:

```markdown
## Experiments
- [Baseline 2D JAX](experiments/baseline-2d-jax.md) — DreamerV3 baseline on HM3D, 2D-only

## Methods
- [DreamerV3 Architecture](methods/dreamerv3-architecture.md) — Our DreamerV3 implementation decisions
```

### log.md format

Append-only. Each entry includes date, operation type, page title, and source:

```markdown
## [YYYY-MM-DD] ingest | <Page Title> | source: /reporter | /wiki | manual
<Brief description of what was added/changed. Which pages were updated.>
```

### Cross-references

Use `[[page-name]]` in `## Related` sections to link pages. When creating or updating a page, check if existing pages should link back to it.

### Tags

Use consistent tags across pages:
- Experiment type: `#baseline`, `#curriculum`, `#3d`, `#2d`
- Topic: `#world-model`, `#dreamerv3`, `#habitat`, `#unite`, `#vggt`
- Meeting: `#meeting`, `#pivot`, `#decision`
- Status: `#wip`, `#blocked`

## Rules

- NEVER modify raw sources in `output/` — the wiki summarizes and references them
- ALWAYS update `index.md` when creating or deleting a page
- ALWAYS append to `log.md` when making changes
- Keep pages focused — split large pages into multiple focused ones
- Use consistent terminology across pages (same terms for same concepts)
