3D-25 · scripts/r2dreamer/collect_offline_buffer.py · H100 PCIe · numbers from two 1500-step rehearsals with --profile (warmup 100, active 1400), one with and one without _save_rgb_png.

TL;DR (v2)

Dropping the per-step PNG write took the loop from 139 ms → 89 ms per step (−35.8 %, ×1.56 faster). 500 k transitions now project to ~12.4 h instead of ~19 h, and the on-disk buffer shrinks ~13× (≈7 GB vs ≈92 GB) because PNG frames were 92 % of the bytes. After the cut, VGGT extraction alone is 86.7 % of every step — it is now the only thing left worth optimizing.

Methodology

Added a StepTimer behind --profile that wraps each block of the inner loop with time.perf_counter(), drops the first --profile-warmup steps (default 100) to skip JAX compile + first scene swap, and dumps a JSON summary at exit. Ran:

uv run scripts/r2dreamer/collect_offline_buffer.py \
    --checkpoint <step_001000000.pkl> \
    --n-steps 1500 --collect-seed 42 \
    --out-dir data/_profile_buffer \
    --profile --profile-warmup 100

In parallel, sampled GPU utilization once a second for 30 s with nvidia-smi dmon -s u -c 30 -d 1 while the rollout was past step 200. JAX dispatch is asynchronous, but the very next line (.astype(np.float16)) reads the VGGT outputs into NumPy, which forces a sync — so the vggt_extract lap captures real GPU wall-clock, not dispatch time.

Appendix: what _save_rgb_png used to do in those 50 ms

Kept here for the record — the function and its call were removed in v2.

The function looks like one line:

def _save_rgb_png(image: np.ndarray, path: Path) -> None:
    Image.fromarray(np.transpose(image, (1, 2, 0))).save(path)

Under the hood, every call walks the full PNG encode pipeline once per frame:

  1. CHW → HWC transpose in NumPy. The frame leaves Habitat as (3, 518, 518) uint8; PIL needs (518, 518, 3). np.transpose returns a non-contiguous view, and Image.fromarray ends up materialising a contiguous copy (~800 KB).
  2. PIL → libpng handoff. PIL.Image.save on a .png path dispatches to the PNG writer, which streams rows into libpng. No multithreading; libpng is single-threaded by design.
  3. Row filter selection. For each of the 518 rows, libpng tries the five PNG filter types (None / Sub / Up / Avg / Paeth) on a sample window and picks the one with the smallest sum of absolute differences. This is the "heuristic" filter strategy, the default in libpng. It's a real per-pixel pass over 518×518×3 bytes — ~800 KB read five different ways.
  4. Deflate (zlib). The filtered rows go through deflate at the default level (6), which builds a sliding-window LZ77 dictionary and Huffman-codes the literals/distances. On natural images PNG compression ratios are modest (~1.5–2×), so we're spending CPU for not much disk savings. libpng calls zlib synchronously — no async / no offload.
  5. CRC + write. Each PNG chunk gets a CRC32 (currently software, not the CPU's CRC32 instruction in libpng's path), then bytes are written to the file. The file is on Lustre/parallel-FS here; the per-frame fsync isn't explicit but the OS still has to journal the metadata for a new ~250 KB file.

So the 50 ms decomposes roughly as: ~3 ms transpose+copy, ~15 ms filter selection, ~25 ms deflate, ~5 ms CRC+write, ~2 ms Python ↔ C boundary. None of it is parallelised, none of it is on the GPU, and every step blocks the next environment step.

Multiply by 500 000 frames and you get ~7 h of pure PNG work on the critical path — and a directory containing 500 k files (~120 GB) that's also a pain for downstream readers. That's why the table puts "replace PNG" ahead of "parallelise envs": PNG is a big slice and a downstream usability problem.

Why not GPU PNG? NVIDIA's nvJPEG/nvJPEG2k exists, and there is some experimental nvPNG work, but there is no production-grade PNG encoder on GPU in the CUDA stack, and shipping the 800 KB raw frame back to the GPU just to encode it would burn the H100→host bandwidth we just saved. The high-leverage moves are (a) keep the raw bytes (skip PNG), or (b) use a format with a hardware-friendly codec — WebP via libwebp is ~3–4× faster than PNG on CPU at similar quality, JPEG-XL is faster still where supported.

Why the CPU is busy (and it isn't Habitat)

The "CPU bound" framing is right, but the culprit is PIL.Image.save writing PNGs, not the simulator. PNG encoding of a 518×518 RGB image is ~50 ms here — PIL uses libpng, single-threaded, with deflate at default level. With 500 k frames that's ~7 hours of pure encode work on the hot path. Habitat-sim itself is tiny on this hardware:

  • Habitat-sim's C++ tick (navmesh, collision, geodesic) is sub-millisecond on an H100 node because the simulator state is small and the navmesh is pre-loaded into RAM.
  • OpenGL/EGL render at 518×518 is a single draw call. With an H100 + recent EGL driver, the render-plus-readback path is fast enough to disappear into the 2.4 ms total env.step budget.
  • The pybind11 Python⇄C++ marshal is microseconds, not the bottleneck.

So when we read "GPU 13 %" out of nvidia-smi --query-gpu, we were looking at a moment between VGGT calls. The real picture is: GPU runs hard during the 78 ms VGGT block, then sits idle for 50 ms while PIL encodes the PNG on the CPU, then idle again for the small CNN forward, then ~2 ms for the OpenGL render. Average GPU SM util ≈ 50 %, which matches the dmon mean.

Speedup brainstorm v2 · VGGT-only

With PNG gone, anything that isn't VGGT is < 6 % of the budget. The remaining levers all sit on VGGT.

#IdeaEstimated winEffortRisk / notes
1 Cut --vggt-total-budget (currently 200 000) and the per-block --vggt-static-budget. Sweep on 5 k-step rehearsals, pick the largest budget that doesn't degrade WP/CP or aggregator cosine vs. the full-budget baseline. 15–25 % Low VGGT is 86.7 % of every step. A small attention-budget reduction directly cuts wall-clock; the cosine integrity check in the verifier already catches loss-of-fidelity above the 0.999 floor.
2 Move VGGT to fp16/bf16 throughout (params + activations). The fp16 readout cast at the buffer boundary already loses no measurable precision (cosine min ≥ 0.9999998 measured here). 15–30 % Medium Need to verify the JAX VGGT loader accepts fp16 weights or supports bf16 mixed precision. Halving the cache also frees GPU memory for parallel workers (idea 4).
3 Swap to FastVGGT (already cloned at external/FastVGGT) — drop-in replacement claiming ~2× speedup for the same outputs. ~40 % Medium Requires plugging FastVGGT into JAXVGGTFeatureExtractor and re-verifying readout cosine. With VGGT at 86.7 %, this is now the single highest-leverage change.
4 Parallel env workers (e.g. 4 subprocesses), each running its own Habitat env + VGGT, sharding the buffer; merge shards at the end. 2–4× High GPU memory: VGGT cache is ~60 GB on this run, so naively replicating is impossible. Either (a) shrink the cache via ideas 1/2 so 2–3 workers fit, or (b) run one shared VGGT server with N env clients over a queue.
5 Replace PIL resize with cv2 (cv2.resize uses SIMD). ~2 % Low Resize is 4.7 ms; cv2 likely halves it. Trivial change, modest gain.
6 Tighten agent.act JIT — currently 4.5 ms / step is mostly dispatch overhead. Skipping the jax.random.split per step would save ~1 ms. ~1 % Low Stop seeding from a per-step PRNGKey split; pull a vector of keys ahead of time.
Spec deviation. The 3D-25 issue listed rgb_frames/ (500 k PNGs at 518×518) in the buffer layout, explicitly to enable re-using the same trajectories for future VGGT readouts without re-rolling. v2 drops PNGs in exchange for ~6.6 h of wall-clock and ~85 GB of disk. The trajectory is still regenerable deterministically (collect_seed=42 + checkpoint SHA), but on-demand RGB recompute means another full rollout, not a cheap re-read. Track on Linear before adopting permanently for downstream consumers.

Suggested two-step path

Quick win (delivered in v2)

Skipped PNG entirely. Measured: 139 → 89 ms/step → 11.2 steps/s. 500 k ETA: ~19 h → ~12.4 h. The 36 h slurm budget now has ~24 h of margin.

Next quick win (1 PR, ~1 day)

Idea 1 (VGGT budget sweep) + idea 5 (cv2 resize). Conservative: 89 → ~70 ms → ~14 steps/s → 500 k in ~10 h.

Real fix (1–2 weeks)

Idea 3 (FastVGGT) or idea 2 (fp16/bf16 VGGT), then optionally idea 4 (parallel envs over a shared VGGT server). Target: ~30–40 ms/step → ~25–35 steps/s → 500 k in ~4–6 h.
