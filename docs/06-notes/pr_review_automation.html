Automatisierte Refactor- und PR-Review-Routine fuer Master-Thesis-3D-VLA

Ziel: PRs sollen automatisch einen hochwertigen Agent-Review bekommen, ohne dass du jedes Mal aktiv neben dem Prozess sitzen musst. Die Pipeline trennt schnelle Cloud/CI-Reviews von echten bwUniCluster-GPU/Habitat-Checks.

Kurzempfehlung

Empfohlenes Setup

Nutze drei Ebenen statt einer grossen magischen Automation:

  1. GitHub PR Auto-Review: Codex Code Review fuer jeden PR aktivieren oder per @codex review triggern.
  2. GitHub Action fuer leichte Agent-Checks: Nicht-GPU-Checks, Diff-Review, Architektur-Review und Testauswahl automatisch auf PRs ausfuehren.
  3. bwUniCluster GPU-Gate: Fuer Habitat/VGGT nur gezielt per self-hosted Runner oder manuell/halbautomatisch via SLURM laufen lassen.
Warum nicht alles in GitHub-hosted CI? Habitat-Sim, VGGT externals, grosse Checkpoints, CUDA/JAX und bwUniCluster-Datasets sind zu environment-spezifisch. GitHub-hosted Runner sind gut fuer CPU-Checks, aber nicht fuer reproduzierbare Habitat/VGGT-GPU-Integration.

Layer 1

Automatischer PR-Review

Codex reviewed den Diff und postet GitHub-Review-Kommentare.

  • Sehr wenig Setup.
  • Folgt AGENTS.md.
  • Gut fuer P0/P1 Bugs, Scope-Fehler, Review-Guidelines.
Layer 2

CI-Agent Workflow

GitHub Action laesst einen wiederholbaren Codex-Prompt laufen.

  • Gut fuer Style, Testauswahl, PR-Body-Qualitaet.
  • Kann Ergebnisse als PR-Kommentar posten.
  • Nicht ideal fuer GPU/Habitat.
Layer 3

Cluster-GPU Gate

SLURM prueft echte VGGT/Habitat-Pfade mit H100.

  • Hohe Aussagekraft.
  • Queue/QOS und Secrets muessen gehandhabt werden.
  • Am besten nur fuer relevante Pfade triggern.

Was automatisch passieren kann

Ausloeser Automatische Aktion Empfohlen fuer dieses Repo
PR opened / synchronize Codex Auto-Review oder @codex review Ja. Das ist der beste erste Schritt.
PR changed files enthalten src/vggt/ Agent markiert: GPU-Integration noetig Ja. Nicht jeden PR braucht VGGT/H100.
PR label needs-gpu SLURM Smoke/Integration auf Cluster starten Ja, aber mit separater Runner/Token-Loesung.
Tests failed Agent fasst Fehler zusammen und schlaegt Fix vor Ja. Fix sollte aber nicht automatisch ungeprueft gemerged werden.

Drei konkrete Architekturen

A. Minimal: Codex Code Review in GitHub

In Codex Code Review Settings fuer das Repository aktivieren. Danach kann ein PR per @codex review reviewed werden; mit Automatic Reviews passiert das bei neuen PRs automatisch.

Gut fuer: Review-Kommentare, Scope-Fragen, offensichtliche Bugs, PR-Guideline-Verstoesse.

Nicht gut fuer: echte Habitat/VGGT Runtime-Garantie.

B. Mittel: GitHub Action mit Codex-Prompt

Eine Workflow-Datei triggert auf PRs und laesst einen fixen Prompt laufen: "Review gegen AGENTS.md, pruefe Testluecken, nenne noetige GPU-Checks, poste Must Fix / Should Fix / Safe to merge". 

name: Codex PR review
on:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  codex-review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
      issues: write
    steps:
      - uses: actions/checkout@v5
        with:
          ref: refs/pull/${{ github.event.pull_request.number }}/merge
      - uses: openai/codex-action@v1
        id: codex
        with:
          openai-api-key: ${{ secrets.OPENAI_API_KEY }}
          prompt-file: .github/codex/prompts/review.md
          output-file: codex-output.md

C. Stark: Self-hosted Runner auf bwUniCluster

Ein GitHub self-hosted runner laeuft auf einer Maschine, die Zugriff auf Repo, venv, Daten, SLURM und Module hat. Der Workflow routet GPU-Jobs auf runs-on: [self-hosted, linux, x64, bwunicluster] und startet intern srun. 

jobs:
  vggt-integration:
    if: contains(github.event.pull_request.labels.*.name, 'needs-gpu')
    runs-on: [self-hosted, linux, x64, bwunicluster]
    steps:
      - uses: actions/checkout@v5
      - run: ./scripts/setup_worktree.sh
      - run: bash scripts/slurm/hooks/link_external.sh
      - run: |
          srun --partition=dev_gpu_h100 --gres=gpu:1 --time=00:30:00 \
            .venv/bin/python -m pytest tests/vggt/test_jax_integration.py -q

GitHub Action vs Self-hosted Runner

Deine Formulierung ist richtig: Die GitHub Action ist der Ausloeser und Ablaufplan. Der self-hosted Runner ist die Maschine, die diesen Plan ausfuehrt.

Begriff Was ist das? Beispiel in diesem Repo
GitHub Action / Workflow YAML-Datei in .github/workflows/. Definiert Trigger, Jobs und Commands. test-bwunicluster.yml startet bei workflow_dispatch und fuehrt SLURM-Diagnose aus.
Runner Die Maschine, auf der ein Job laeuft. ubuntu-latest ist GitHub-hosted; self-hosted ist deine eigene Maschine.
Self-hosted Runner Ein von dir installierter GitHub Actions Runner, z.B. auf einer bwUniCluster-nahen Maschine. Kann squeue, sacct, srun, Repo-venv und Dataset-Pfade sehen.
SLURM Job Der eigentliche Cluster-Job, den der Runner mit srun oder sbatch startet. VGGT/Habitat-GPU-Tests laufen als H100-Job, nicht direkt im GitHub-Runner-Prozess.

Kurz: on: pull_request oder workflow_dispatch entscheidet, wann der Workflow startet. runs-on: self-hosted entscheidet, wo er laeuft.

Self-hosted Runner Setup fuer bwUniCluster

Was ich vorbereiten kann

  • Workflow-YAML fuer manuelle oder label-gesteuerte GPU-Gates schreiben.
  • Runner-Labels vorschlagen, z.B. self-hosted, linux, x64, bwunicluster, slurm.
  • SLURM-Testkommando und VGGT-Integrationstest als Workflow-Schritte definieren.
  • Review-Prompt fuer leichte Agent-Checks vorbereiten.

Was du in GitHub machen musst

  1. In GitHub zu Settings -> Actions -> Runners gehen.
  2. New self-hosted runner auswaehlen.
  3. Linux x64 auswaehlen und den angezeigten Download-/Configure-Befehl kopieren.
  4. Den kurzlebigen Runner-Token nicht committen und nicht in Chat/Logs posten.
  5. Runner mit Labels registrieren, z.B. bwunicluster,slurm.

Die konkrete Version und der Token kommen von GitHub. Das hier ist nur die Form.

Empfohlene Betriebsweise

  • Am Anfang interaktiv mit ./run.sh starten, nicht sofort als dauerhafter Service.
  • Nur private/trusted PRs auf self-hosted Runner lassen.
  • GPU-Workflow nicht automatisch fuer Fork-PRs ausfuehren.
  • Fuer echte GPU-Tests im Workflow weiter srun verwenden.

Sicherer Workflow-Trigger

on:
  workflow_dispatch:
  pull_request:
    types: [labeled, synchronize, reopened]

jobs:
  vggt-gpu:
    if: >
      github.event_name == 'workflow_dispatch' ||
      (
        github.event.pull_request.head.repo.full_name == github.repository &&
        contains(github.event.pull_request.labels.*.name, 'needs-gpu')
      )
    runs-on: [self-hosted, linux, x64, bwunicluster, slurm]

Damit laeuft der GPU-Gate automatisch nur fuer PRs aus demselben Repo mit Label needs-gpu. Manuell kann er immer ueber workflow_dispatch gestartet werden.

Wo sollte es laufen?

Ort Geeignet fuer Risiko / Aufwand Empfehlung
Lokal / Codex App Interaktive Refactors, HTML-Review, kleine CPU-Checks, PR-Erstellung Haengt an deinem Rechner/Session; nicht voll unattended Gut fuer Entwicklung, nicht als alleiniger Merge-Gate.
GitHub-hosted Cloud Runner Lint, PyCompile, CPU-Unit-Tests, Agent-Review, PR-Kommentar Habitat/VGGT Environment schwer; GPU/Checkpoints/Datasets unklar Ja fuer leichte Gates, nein fuer echte VGGT/Habitat-Garantie.
GitHub larger GPU Runner Generische CUDA-Tests ohne Cluster-Datasets Kosten/Verfuegbarkeit; Habitat-Sim und Daten muessen installiert werden Optional, aber wahrscheinlich weniger reproduzierbar als bwUniCluster.
bwUniCluster self-hosted Runner VGGT, Habitat, SLURM, echte Daten, H100, bestehende venv/external Links Sicherheits-/Token-Frage, Runner-Lifetime, Queue/QOS, Netzwerk Beste technische Passung fuer GPU-Gates, aber sauber isolieren.

Repo-spezifische Review-Routine

Fuer dieses Repo sollte ein automatischer Review-Prompt nicht generisch sein. Er sollte die vorhandenen Regeln aus AGENTS.md direkt nutzen:

  • Review gegen linked issue / acceptance criteria, nicht gegen beliebige Verbesserungen.
  • Keine opportunistischen Refactors ausserhalb des Scopes.
  • VGGT/Habitat-Aenderungen brauchen eng passende Runtime-Verifikation.
  • Worktree-Setup pruefen: ./scripts/setup_worktree.sh und fuer VGGT link_external.sh.
  • Review-Ausgabe in drei Gruppen: Must fix, Should fix soon, Safe to merge.
# .github/codex/prompts/review.md
Review this pull request against the nearest AGENTS.md only.

Return:
1. Must fix before merge
2. Should fix soon
3. Safe to merge

Focus on:
- acceptance criteria gaps
- runtime regressions
- broken VGGT/Habitat/cache behavior
- missing targeted tests
- unrelated scope expansion

For VGGT/Habitat changes, explicitly state whether GPU/SLURM verification is required.

Pragmatische Roadmap

  1. Heute: Codex Code Review in GitHub aktivieren und AGENTS.md um Review-Guidelines ergaenzen.
  2. Naechster Schritt: GitHub Action fuer CPU/Agent-Review mit Prompt-Datei anlegen.
  3. Danach: Label needs-gpu einfuehren; Agent setzt es oder reviewer setzt es manuell.
  4. Cluster-Pilot: self-hosted Runner nicht direkt auf Login-Node dauerhaft offen betreiben; lieber kontrollierter Runner-Service oder manuell ausgeloester SLURM-Gate.
  5. Merge-Regel: PR darf erst "ready" sein, wenn entweder CPU-Gates reichen oder der GPU-Gate-Status dokumentiert ist.
