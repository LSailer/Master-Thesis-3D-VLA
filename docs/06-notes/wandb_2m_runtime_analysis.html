Recommended SLURM strategy

Stop treating 48h as enough for these families. The current runs need either longer walltime or automatic resume chaining.

  • WP/CP 37, WP/CP 64, L2-L4 flatten, agg-MLP, agg-avg: request at least 72h when available, or submit chained 48h jobs with resume from the latest checkpoint. Memory can stay at 64G for 37/flatten/avg and 128G for WP/CP64 if you keep current safety margin.
  • Hybrid CNN+VGGT and hybrid norm fixed: use 96h or chained 48h resumes. Disable or greatly reduce validation/video cadence for production-to-2M, because logs show repeated wandb: Encoding video... near timeout and prior profiling showed evaluation/video overhead is material.
  • Raw aggregator variants: do not prioritize direct 2M reruns. First shrink the representation via pooling/projection or run a smaller proof with explicit memory/throughput budget. Current raw jobs use 45-53GB RSS and only about 6k steps/h.
  • Checkpoint/resume: rely on the existing save_every=50000 checkpoints and launch follow-up jobs with the same run family/name plus explicit resume/run-id handling, so W&B does not look like an unrelated crash when SLURM time expires.
  • Rerun order: first l1-agg-mlp-cap500k, L3/L2 WP/CP flatten, wpcp37-cap500k, and agg-avg e256/e512/e1024 if the goal is fastest 2M completion; defer raw aggregator.
