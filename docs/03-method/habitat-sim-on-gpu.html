Running habitat-sim on GPU — overview

Companion to offline-buffer-collection-perf.html · what can move to the GPU, what stays on the CPU, and how to ship the change

TL;DR

habitat-sim is not a GPU world model. Physics (Bullet), the navmesh / pathfinder, and the agent integrator run on the CPU by design — there is no full-GPU mode you can flip on. What you can move to the GPU is the render + readback path and the way you scale environments:

  • gpu2gpu_transfer=True — kills the GPU→CPU memcpy on the sensor output (CUDA-GL interop → PyTorch tensor in place). Needs habitat-sim built --with-cuda.
  • EnvBatchRenderer (habitat-lab) — N environments rasterized in one render pass, asset cache loaded once. Big win when you have many envs.
  • GPU depth unprojection shader — depth never round-trips CPU.
  • Multi-process scaling — habitat-sim is well-known for > 10 000 fps on a single GPU when you fan out workers.

If you genuinely want physics on the GPU, habitat-sim is the wrong tool — look at ManiSkill3 / Isaac Lab.

The current pipeline, drawn out

Each env.step() in your collector today crosses CPU and GPU like this:

pybind11 + sim tick (Bullet, navmesh, geodesic)
waits on GPU
readback → np.ndarray
PIL · npz · bookkeeping
GPU
idle
OpenGL draw 518²
idle (GL→CPU memcpy)
VGGT
CPU work (sim, glue, encode) GPU work (render, VGGT) GPU→CPU readback (forced sync)

The red block is what gpu2gpu_transfer removes. The blue sim block is what no habitat-sim flag can remove — it is C++ on the CPU by design.

Navmesh / pathfinder on GPU Not supported. The pathfinder (Detour/Recast) is CPU-only. — N/A
Subtle point. "Running on GPU" can mean two very different things: (1) output stays on GPU — purely a memcpy optimization, (2) simulation logic itself runs on GPU — habitat-sim does not do this. The 13 % GPU utilization in your run is mostly bottlenecked by (2), so (1) alone won't fix it.

Enabling gpu2gpu_transfer — the smallest useful change

If your build was compiled with CUDA (BUILD_WITH_CUDA=ON / python setup.py install --with-cuda), flip the flag on the sensor spec when you build the simulator config:

import habitat_sim

rgb_sensor = habitat_sim.CameraSensorSpec()
rgb_sensor.uuid = "rgb"
rgb_sensor.sensor_type = habitat_sim.SensorType.COLOR
rgb_sensor.resolution = [518, 518]
rgb_sensor.position = [0.0, 1.25, 0.0]
rgb_sensor.gpu2gpu_transfer = True   # <-- here

# observations["rgb"] is now a torch.cuda.Tensor, not an np.ndarray.
# Feed it straight into VGGT without going through CPU.

Check first whether your wheel was built with CUDA:

python -c "import habitat_sim; print(habitat_sim.cuda_enabled)"

If that prints False, the conda wheels you have don't support it — you'd need to rebuild from source on bwUniCluster with CUDA toolkit available, which is non-trivial.

Why this matters for your stack. Right now the 518² RGB frame goes GPU → CPU (np.ndarray) → CPU → GPU (JAX VGGT input). With gpu2gpu_transfer + a small bridge to JAX (via DLPack), the frame never leaves the GPU. That alone is worth ~5–15 ms / step on a 518² frame, and removes a forced sync that today is serializing VGGT behind the readback.

Enabling EnvBatchRenderer — when you scale to N envs

EnvBatchRenderer is the right move once you go to multiple parallel envs (idea #2 in the perf doc). Instead of N processes each issuing their own draw call, the lab pipeline collects per-env keyframes and renders them all at once.

  • Set habitat.simulator.renderer.enable_batch_renderer = True in the structured config.
  • Use a VectorEnv with num_environments > 1.
  • Composite GLTF assets are pre-loaded once → memory per extra env drops dramatically. This matters because each habitat-sim instance otherwise reloads the HM3D scene.

For your numbers: 4 envs × ~6 SPS today ≈ 24 SPS, but with the batched renderer the asset overhead per extra env collapses and you should comfortably saturate the H100's render throughput long before you saturate the SMs with VGGT.

What's the realistic ceiling?

+ 4 parallel envs, shared VGGT server ~30–40 Parallel CPU sim hides each other's latency. VGGT batched across envs.
+ EnvBatchRenderer (8 envs) ~60–100 Single render pass for all envs; asset cache shared.
habitat-sim reported max ~10 000 fps Multi-process, tiny resolution, no VGGT, no PNG. Useful as an upper bound, not as your target.

If you really want fully-GPU simulation

habitat-sim is not designed for this. If physics-on-GPU is the goal — e.g. to push past ~100 SPS on a single H100 without spinning up many CPU workers — the realistic options are:

  • ManiSkill3 — GPU-parallel robot sim + rendering, explicitly built for high-throughput embodied AI. Reports thousands of envs in lockstep on one GPU.
  • Isaac Lab / Isaac Sim — NVIDIA's GPU-native sim with PhysX-on-GPU.
  • Madrona Engine — research-grade fully GPU-resident simulator used for million-step-per-second benchmarks.

Switching is a big move (no HM3D scene parity, no Habitat ObjectNav benchmark) — only worth it if your thesis story is "scaling the data engine", not "3D features for ObjectNav".

Don't skip the measurement step. gpu2gpu_transfer looks free, but it forces VGGT and habitat-sim to share a CUDA context — there have been past reports of conflicts when JAX and PyTorch contend for the same device. Run a short rehearsal (1 000 steps) with the flag flipped before committing the change to the slurm submission.
