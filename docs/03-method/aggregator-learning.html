How the Aggregator works

A 24-layer transformer tower that turns a stack of RGB frames into geometry-aware tokens — by alternating attention within each frame and across all frames. Your JAX port adds a streaming KV-cache with diversity-based eviction. Let's build it up piece by piece.

1The big picture

Before any detail: the Aggregator is one stage in a pipeline. RGB comes in, geometry-aware tokens come out, and a small pooling step hands a fixed vector to your world-model encoder.

👆 Click any stage to see what it does and the tensor shape at that point.

The one-sentence version: DINOv2 turns each frame into 1369 patch tokens; the Aggregator prepends 5 special tokens, then runs 24 blocks that alternate between attending inside a frame (spatial) and across frames (temporal), producing rich per-token features the world model can read.

2Token layout: what are these 1374 things?

Every frame becomes a sequence of 1374 tokens, each a 1024-dim vector. They are not all the same kind. The ordering is fixed and load-bearing — downstream code slices by index.

How the special tokens get their values (the slice_expand_and_flatten trick)

The learned parameters have shape (1, 2, X, C) — note the 2. Slot 0 is used for frame 0, slot 1 for every other frame. So the very first frame of an episode gets a distinct camera/register embedding from the rest — it sets the reference context.

def _slice_expand_and_flatten(token_tensor, B, S):  # token: (1, 2, X, C)
    query  = broadcast(token_tensor[:, 0:1], (B, 1,   X, C))  # frame 0
    others = broadcast(token_tensor[:, 1:2], (B, S-1, X, C))  # frames 1..S-1
    return concat([query, others], axis=1).reshape(B*S, X, C)

In streaming mode there's no S to expand: it just picks slot = 0 if past_frame_idx==0 else 1.

Why register tokens? They're learnable "attention sinks" (from DINOv2-reg). Attention often needs somewhere to dump probability mass; without sinks that junk lands on real patches and creates artifacts. They carry no spatial meaning — which is exactly why the pooling step (§9) drops them.

3Where is each token? — 2D rotary positions

The tower has no learned positional embedding for patches. Instead it uses 2D RoPE: position is injected by rotating the query/key vectors by an angle that depends on the patch's (y, x) grid coordinate. Each patch knows where it sits on the 37×37 grid.

The position grid

Hover a cell to read its assigned position. Special tokens all sit at (0,0); patch (row,col) gets (row+1, col+1).

Why +1 on every patch?

The special tokens occupy position (0,0). To keep patches from colliding with them, every patch coordinate is shifted up by one:

patch_pos = (y, x) + 1
special   = (0, 0)        # cam + 4 register
pos = concat([special, patch_pos])

RoPE tables are built once per forward with

$$\text{dim}=\tfrac{d_{head}}{2}=32,\quad \text{max\_pos}=38,\quad f=100$$

Head dim 64 is split in half: one half rotates by the row angle, the other by the column angle. That's what makes it 2D.

4The core idea: frame ⇄ global attention

This is the heart of the whole design. Each of the 24 layers does two attention passes in order — and the trick is they operate on different reshapes of the same tensor. No new data; just a view change that decides who attends to whom.

Squares are tokens; color bands group them by frame. The dashed boxes show what a single attention call mixes together.

FRAME

Within a frame — spatial

Tensor is viewed as (B·S, P, C). Each frame attends only to its own 1374 tokens. This is where patches relate to each other spatially (object surfaces, edges, layout).

GLOBAL

Across frames — temporal

Tensor is reshaped to (B, S·P, C). Now every token can see tokens in other frames — this is how multi-view 3D consistency and motion get integrated.

The masking subtlety. In the offline (no-cache) path, global attention uses a causal frame mask: frame i may only attend to frames 0…i, never the future. In streaming mode that mask is unnecessary — the new frame is the only query, and it attends to the cached past.

5The forward loop, one block at a time

Step through the 24 iterations. Each one: run the frame block, run the global block, then concatenate both intermediates along the feature axis and append to the output list. That last detail surprises people — the output width is 2048, not 1024.

The actual loop body (JAX port) 
for b in range(self.depth):           # 24
    tokens_frame = _to_frame(tokens)                # (B*S, P, C)
    tokens_frame = Block(..., name=f"frame_blocks_{b}")(tokens_frame, ...)
    frame_inter  = tokens_frame.reshape(B, S, P, C)

    tokens_global = _to_global(tokens_frame)        # (B, S*P, C)
    tokens_global = Block(..., name=f"global_blocks_{b}")(tokens_global, ...)
    global_inter  = tokens_global.reshape(B, S, P, C)

    tokens = _to_frame(global_inter)                # feed next block
    output_list.append(concat([frame_inter, global_inter], axis=-1))  # (B,S,P,2C)

Note the data flow: the global output is what flows into the next block. The frame output is only stashed for the concatenated record.

What's inside one Block?

Standard pre-norm transformer block with LayerScale (a learnable per-dim residual gain, init 0.01) and QK-norm:

x = x + ls1( attn( norm1(x) ) )    # LayerNorm eps 1e-5
x = x + ls2( mlp ( norm2(x) ) )    # MLP: 1024 → 4096 → 1024, exact GELU

Attention has QK-LayerNorm, 2D RoPE on Q and K, and a manual fp32 softmax in the offline path (cuDNN flash in the cached path).

6Streaming KV-cache: the part you added

The reference processes all S frames at once. For an RL agent walking through HM3D, that's wasteful — frame t shouldn't recompute attention over frames 0…t-1 every step. Your JAX port adds a KV-cache: process S=1 new frame per call, and let global blocks read the past frames' keys/values from past_kvs[i].

📦 Offline path use_cache=False

  • All S frames in one go
  • Global attn uses an S·P causal mask
  • Used for parity tests vs. the reference

🌊 Streaming path use_cache=True

  • One frame per call, past_frame_idx tracks position
  • Each global block returns updated K/V
  • No mask needed — current frame attends to cached past

Two cache formats

FormatShapeWhen
Legacy 2-tuple (k, v)variable lengthParity tests calling the aggregator directly. Eviction yields a compact concat.
Padded 3-tuple (k_pad, v_pad, valid_len)(B, H, MAX, Dh)The feature extractor. Fixed shape + traced int32 valid_len → jittable without shape polymorphism.
Why padded? JIT hates changing shapes. By pre-allocating (B,H,MAX,Dh) and tracking how many slots are valid with an int32 scalar, the whole streaming step compiles once. New K/V is written with dynamic_update_slice_in_dim at offset valid_len; attention uses cuDNN flash with key_value_seq_lengths so it ignores padded slots.

7Eviction playground: which tokens survive?

The cache can't grow forever. When it exceeds a per-block budget, the block evicts. The rule is the interesting bit, and it's counter-intuitive: the most redundant tokens are thrown away, the most diverse are kept.

The first num_anchor_tokens (= P, the current frame) are always kept as anchors. Among the remaining candidates, each key is L2-normalized, a mean direction is computed, and each token is scored by cosine similarity to that mean:

$$\text{score}_i = \hat{k}_i \cdot \bar{k}, \qquad \bar{k}=\text{mean}_j\,\hat{k}_j$$

High score = points the same way as everyone else = redundant → evicted. We keep the budget − anchors lowest-scoring (most diverse) candidates via top_k(−score).

The eviction code (legacy compact path) 
def _evict_kv(k, v, cache_budget, num_anchor_tokens):
    B,H,N,D = k.shape
    if N <= cache_budget: return k, v, None      # nothing to do
    n_keep = cache_budget - num_anchor_tokens
    anchor_k, cand_k = k[:,:,:n_anchor], k[:,:,n_anchor:]
    cand_k_norm = cand_k / norm(cand_k)                # L2 normalize
    mean_vec = mean(cand_k_norm, axis=2)
    scores   = sum(cand_k_norm * mean_vec, axis=-1)  # cosine to mean
    _, top_idx = top_k(-scores, n_keep)                # keep LOWEST scores
    final_k = concat([anchor_k, gather(cand_k, top_idx)])
    return final_k, final_v, mean(scores)              # avg_score → feeds budgets
The returned avg_score matters later. A block that just evicted a pile of high-similarity tokens reports a high average score. §8 uses that signal to give such blocks a smaller budget next time — they clearly hold redundant stuff.

8Dynamic per-block budgets

The total_budget is split across the 24 blocks — but not evenly. Blocks whose cache was full of redundancy (high last score → low "diversity") get a smaller slice. It's a softmax over diversity:

$$\text{diversity}=1-\text{score},\quad \text{budget}_b = \text{total}\cdot \mathrm{softmax}\!\left(\frac{\text{diversity}}{0.5}\right)_b$$

9Consuming the output: pooling to a vector

The tower returns a list of 24 tensors of shape (B,S,P,2048). For your "aggregator" feature variant, the adapter takes the final tokens and pools them into one fixed vector for the world-model encoder. Three pools, by token type:

patches = features[5:]           # drop the 4 register sinks
mean_p  = patches.mean(axis=0)   # smooth global summary
max_p   = patches.max(axis=0)    # salient features
return concat([cam, mean_p, max_p])  # (3*D,) → RMSNorm + MLP encoder

Register tokens (indices 1–4) are deliberately dropped — they're attention sinks with no spatial meaning. The camera token is kept separate because VGGT's own camera_head reads it for pose.
