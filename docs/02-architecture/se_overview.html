Software Engineering for ML Research

A practical overview of modules, components, interfaces — and patterns to structure a Python/ML codebase so it stays readable as it grows. Tuned to your DreamerV3 + 3D-vision (VGGT/UNITE) thesis context.

1. Why this matters

Research code earns a bad reputation for a simple reason: every experiment is "the last one". So globals creep in, training scripts copy-paste, hyperparameters live as magic numbers, and three months later nobody — including you — can rerun the result that went into the thesis.

Software engineering is the small, boring set of habits that prevents this. The vocabulary you need is short: module, component, interface, plus a handful of principles (separation of concerns, dependency injection, explicit configuration). Apply them consistently and the code roughly maintains itself. This guide gives you both the vocabulary and the Python/ML-specific recipes.

2. Module, component, interface — the core trio

Concept

Module

The smallest unit of code organization. In Python a module is a single .py file; a package is a directory of modules with an __init__.py. A module groups related functions, classes, and constants behind one importable name.

Mental model: a module is a chapter in a book — it has a topic, you can read it independently, and you find it in the table of contents (the directory tree).

Concept

Component

A self-contained unit of functionality with one well-defined responsibility. Bigger than a module: it can span multiple modules. Components communicate with the rest of the system only through their interface, not by reaching into each other's internals.

Mental model: a component is a kitchen appliance. The toaster has buttons (interface) and a job (toast bread). You don't open it up to use it. Replacing it with a fancier toaster doesn't require rewiring the kitchen.

In your project: "the data loader", "the VGGT encoder", "the replay buffer", "the W&B logger" are all components.

Concept

Interface

The contract a component exposes — what callers can rely on, with everything else hidden. Two halves: the signature (function names, argument types, return types) and the behavior (what those functions promise to do).

Why interfaces matter: they're the seam where you can swap one implementation for another. If train() takes a FeatureEncoder interface, you can plug in VGGT today, UNITE tomorrow, and a learned baseline next week — without rewriting train().

Supporting vocabulary you should also know

TermOne-line meaningSmell when violated
CohesionThings in one module belong together (do one job).A utils.py with 47 unrelated helpers.
CouplingHow much one module depends on another's internals.Editing the encoder forces edits in the trainer.
AbstractionExpose what, hide how.Callers passing internal state objects around.
EncapsulationState + the operations on it live together.Free-floating mutations of attributes from outside the class.

Single source of truthEach fact (config, hyperparameter, schema) lives in exactly one place.Same learning rate appears in three configs.

Goal: high cohesion within a module, low coupling between modules. Everything else is a corollary.

3. Cross-cutting principles (the SOLID-lite version)

You don't need the full enterprise-Java treatment. Three principles carry 90% of the value for ML code:

Principle

Single responsibility

Each module/class does one thing. If you have to use the word "and" to describe what a class does, split it. VGGTEncoderAndLossComputer is two classes wearing a trench coat.

Principle

Depend on interfaces, not implementations

Code at the top of the call stack should accept any encoder, not specifically VGGTEncoder. That's what makes ablations cheap.

Principle

Dependency injection

A component receives its collaborators as arguments instead of constructing them itself or pulling from a global. In Python this just means "pass things to functions and constructors". No DI framework needed.

Bad vs good — DI in practice

✗ Hidden dependencies

import wandb
from mypkg.models import VGGT

class Trainer:
    def __init__(self):
        self.encoder = VGGT()        # hard-wired
        wandb.init(project="thesis") # global side effect
        self.lr = 3e-4               # magic number

✓ Constructor injection

class Trainer:
    def __init__(self, encoder, logger, lr):
        self.encoder = encoder
        self.logger  = logger
        self.lr      = lr

# wiring at the program edge
def build_trainer(cfg):
    enc = make_encoder(cfg.encoder)
    log = make_logger(cfg.logger)
    return Trainer(enc, log, cfg.lr)

The pattern: wiring lives at the edge (main or a build_* factory); business logic in the middle takes injected dependencies. Tests pass fakes. Experiments swap implementations via config.

4. Python — structuring the code

4.1 Modules and packages, concretely

mypkg.py # file module — import mypkg mypkg/ # directory (regular) package __init__.py # marks it as a package; can be empty train.py # import mypkg.train models/ __init__.py encoder.py # import mypkg.models.encoder

The __init__.py runs the first time anything in the package is imported. Three sensible things to put there: the version string, curated re-exports for the public API, or nothing at all.

4.2 src/ layout vs flat layout — pick src/

Flat layout (avoid)

myproj/ pyproject.toml mypkg/ __init__.py train.py tests/

src/ layout (preferred)

myproj/ pyproject.toml src/ mypkg/ __init__.py train.py tests/

With a flat layout, Python automatically picks up mypkg/ from the current directory — so import mypkg may use the uninstalled source, silently masking packaging bugs. With src/, import mypkg only works if the package is actually installed (typically uv pip install -e . or pip install -e .). What you test is what users get.

4.3 Public vs private API

Python has no private keyword. Convention does the work:

  • Leading underscore = "internal, do not import from outside" (e.g. _init_weights).
  • The package's public API is what __init__.py re-exports.
  • __all__ declares the public surface and controls from pkg import *.
# src/mypkg/models/encoder.py
def build_encoder(dim: int) -> "Encoder":
    return Encoder(dim, _init_weights())

def _init_weights():        # underscore = internal
    ...

class Encoder:
    ...

# src/mypkg/models/__init__.py — curate the public surface
from .encoder import Encoder, build_encoder
from .decoder import Decoder

__all__ = ["Encoder", "Decoder", "build_encoder"]

Now downstream users write from mypkg.models import Encoder and don't depend on file layout. You're free to rename or split encoder.py later — as long as the public name still resolves, nothing breaks.

4.4 Type hints and data containers

Type hints are documentation the computer can verify. They make signatures self-explanatory and let mypy/pyright catch shape and None bugs before training runs. For "bag of fields" objects, pick the right container:

ToolWhen to use
@dataclassInternal config / state. Pure stdlib, zero deps.
pydantic.BaseModelAnything parsed from disk / CLI / network — needs runtime validation.
TypedDictA dict whose keys are known statically (e.g. dataset items).
NamedTupleTiny immutable record where positional unpacking (x, y = point) is convenient.
 
from dataclasses import dataclass, field
from pydantic import BaseModel, Field
from typing import TypedDict

@dataclass(frozen=True, slots=True)
class TrainState:                  # internal, immutable, hashable
    step: int
    lr: float
    losses: list[float] = field(default_factory=list)

class TrainConfig(BaseModel):      # parsed from YAML / CLI; validated
    lr: float = Field(gt=0, le=1)
    batch_size: int = Field(ge=1)
    encoder: str

class Episode(TypedDict):          # shape of a dict from a dataset
    rgb: "torch.Tensor"
    action: int
    reward: float
Pitfall Mutable default values: losses: list = [] shares one list across every instance. Always use field(default_factory=list) (dataclass) or Field(default_factory=list) (Pydantic).

5. Interfaces in Python: Protocol vs ABC

Python gives you two ways to express an interface. Knowing when to use which is one of the highest-leverage skills for keeping research code modular.

typing.Protocolabc.ABC
StyleStructural ("if it quacks…")Nominal ("must inherit")
Where checkedStatically by mypy/pyrightAt runtime via isinstance
Implementer needs to know about it?NoYes — must subclass
Best forPlug-in points (encoders, datasets, loggers)Sharing implementation through inheritance, or runtime gates

✓ Protocol — flexible, no inheritance

from typing import Protocol, runtime_checkable
import torch

@runtime_checkable
class FeatureEncoder(Protocol):
    out_dim: int
    def encode(self, rgb: torch.Tensor) -> torch.Tensor: ...

class VGGT:                     # no inheritance!
    out_dim = 1024
    def encode(self, rgb): ...

class UNITE:
    out_dim = 768
    def encode(self, rgb): ...

def train(encoder: FeatureEncoder, loader): ...   # accepts both

ABC — when you want shared base behavior

from abc import ABC, abstractmethod

class FeatureEncoder(ABC):
    @abstractmethod
    def encode(self, rgb): ...

    def freeze(self):           # shared helper
        for p in self.parameters():
            p.requires_grad_(False)

class VGGT(FeatureEncoder):     # must inherit
    def encode(self, rgb): ...

Rule of thumb for ML code: reach for Protocol first. Use ABC only when you genuinely need to share method implementations through inheritance, or when callers rely on isinstance checks at runtime.

6. Configuration management

The single biggest readability lever in research code is killing argparse soup and globals in favor of explicit, composable configs.

ToolSweet spot
argparseOne-file scripts, <10 flags. Stdlib.
pydantic-settingsApps that load from env vars + .env; want type validation.
OmegaConfYAML with variable interpolation; no composition needed.
HydraResearch with many experiment variants, sweeps, multirun. Built on OmegaConf.

Hydra in 30 seconds

# conf/config.yaml
defaults:
  - encoder: vggt        # picks conf/encoder/vggt.yaml
  - _self_

steps: 100_000
# train.py
import hydra
from omegaconf import DictConfig

@hydra.main(version_base=None, config_path="conf", config_name="config")
def main(cfg: DictConfig) -> None:
    trainer = build_trainer(cfg)
    trainer.fit()
# swap encoder
python train.py encoder=unite lr=1e-3

# multirun sweep — no bash loops
python train.py --multirun lr=1e-3,3e-4,1e-4 encoder=vggt,unite
Pitfall Letting an untyped DictConfig flow deep into your code. Convert it to a Pydantic model or dataclass at the boundary (Hydra's "structured configs" or OmegaConf.to_object) so the rest of your code sees real Python types and your IDE can autocomplete.

Conventions baked in:

  • Code lives under src/, imported as mypkg.data.hm3d — never as data.hm3d.
  • conf/, tests/, scripts/, notebooks/, outputs/ are siblings of src/, not inside it.
  • Sub-packages mirror concerns, not file types. No classes/ or functions/ directories.
  • tests/ mirrors src/mypkg/ so the test for models/encoders/vggt.py sits at tests/models/encoders/test_vggt.py.

8. The four layers of an ML codebase

Every well-organized PyTorch project — even small ones — has these four layers, even if not labeled. The point of separating them is that you can swap one without touching the others.

Data→ load bytes, decode, transform, batch (Dataset, DataLoader, transforms)
Model→ define f(x; θ) (nn.Module subclasses, encoder/decoder/head)
Training→ compute loss, take gradient steps, schedule LR (optimizer, scheduler, loss)
Eval / Inference→ score, log, visualize (torchmetrics, checkpointing, plots)

Smell — everything mixed together

✗ One file does it all

class Trainer:
    def __init__(self):
        self.imgs = sorted(glob.glob("/home/luca/data/hm3d/*.png"))
        self.encoder = nn.Sequential(
            nn.Conv2d(3, 64, 3), nn.ReLU(),
            nn.Conv2d(64, 128, 3),
        ).cuda()
        self.opt = torch.optim.Adam(self.encoder.parameters(), lr=3e-4)

    def run(self):
        for epoch in range(100):
            for path in self.imgs:
                x = cv2.imread(path)
                x = torch.from_numpy(x).cuda()
                z = self.encoder(x)
                loss = z.pow(2).mean()
                loss.backward(); self.opt.step()
                if epoch % 10 == 0:
                    print("metric", z.std())

✓ Refactored — each layer in its place

# src/data/objectnav.py
class ObjectNavFrames(Dataset):
    def __init__(self, root, transform=None): ...

# src/models/encoders/vggt.py
class VGGTEncoder(nn.Module):
    def __init__(self, ckpt, freeze=True): ...

# src/training/lit_world_model.py

        self.save_hyperparameters(ignore=["model"])

# src/eval/metrics.py

Each file is now testable in isolation: you can unit-test ObjectNavFrames without a GPU and benchmark VGGTEncoder without touching the trainer.

9. Registry & factory pattern

When you have N encoders, M world-model variants, K policies, and want to combine them via config strings, registries beat if/elif chains.

# src/models/registry.py
from typing import Callable, Dict
import torch.nn as nn

_MODEL_REGISTRY: Dict[str, Callable[..., nn.Module]] = {}

def register_model(name: str | None = None):
    def decorator(fn):
        key = name or fn.__name__
        if key in _MODEL_REGISTRY:
            raise KeyError(f"Model '{key}' already registered")
        _MODEL_REGISTRY[key] = fn
        return fn
    return decorator

def create_model(name: str, **kwargs) -> nn.Module:
    if name not in _MODEL_REGISTRY:
        raise KeyError(f"Unknown model '{name}'. Available: {list(_MODEL_REGISTRY)}")
    return _MODEL_REGISTRY[name](**kwargs)
# src/models/encoders/vggt.py
from src.models.registry import register_model

@register_model("vggt_base")
def vggt_base(ckpt_path: str, freeze: bool = True):
    return VGGTEncoder(ckpt_path=ckpt_path, freeze=freeze)

@register_model("vggt_large")
def vggt_large(ckpt_path: str, freeze: bool = True):
    return VGGTEncoder(ckpt_path=ckpt_path, freeze=freeze, variant="large")
from src.models.registry import create_model
encoder = create_model("vggt_base", ckpt_path="/ckpts/vggt.pt")
Tip If you're already using Hydra's _target_: src.models.encoders.vggt.VGGTEncoder for instantiation, you don't strictly need a registry — Hydra does the same job. Pick one approach and stick to it; mixing both is a smell.

10. PyTorch Lightning — when it helps and when it hurts

LightningModule organizes (not abstracts) PyTorch into six methods: __init__, training_step, validation_step, test_step, predict_step, configure_optimizers. Everything else (devices, DDP, mixed precision, checkpointing) is handled by the Trainer.

import lightning as L
import torch.nn.functional as F

class LitVGGTPretrain(L.LightningModule):
    def __init__(self, encoder, lr: float = 3e-4):
        super().__init__()
        self.save_hyperparameters(ignore=["encoder"])
        self.encoder = encoder

    def training_step(self, batch, _):
        x, y = batch
        loss = F.mse_loss(self.encoder(x), y)
        self.log("train/loss", loss)
        return loss

    def configure_optimizers(self):
        return torch.optim.AdamW(self.parameters(), lr=self.hparams.lr)

trainer = L.Trainer(max_epochs=50, accelerator="gpu", precision="bf16-mixed")
trainer.fit(model, datamodule)

✓ Use Lightning for…

  • Standard supervised training (your VGGT/UNITE perception pretraining or fine-tuning).
  • Free DDP / FSDP / mixed precision / multi-GPU SLURM with no code changes.
  • Free callbacks (early stopping, LR monitor, model summary, W&B integration).

✗ Don't use Lightning for…

  • DreamerV3-style world model + actor-critic. Training step isn't "one batch in, one loss out" — it's collect → buffer → sample → train WM → imagine → train actor → train critic. Lightning's contract fights you.
  • Custom CUDA kernels with tight inner loops where hooks add overhead.
  • Anything where you want full ownership of for batch in loader: loss.backward().
Recommendation For your thesis, use Lightning for the supervised perception parts (VGGT adapter, UNITE fine-tuning, segmentation heads). Write the DreamerV3 RL loop as plain PyTorch in a Trainer class you own. Don't be religious about the framework.

11. Reproducibility — the floor

Seed everything

import os, random, numpy as np, torch

def seed_everything(seed: int, deterministic: bool = False):
    random.seed(seed)
    np.random.seed(seed)
    torch.manual_seed(seed)
    torch.cuda.manual_seed_all(seed)
    os.environ["PYTHONHASHSEED"] = str(seed)
    if deterministic:
        torch.use_deterministic_algorithms(True, warn_only=True)
        torch.backends.cudnn.deterministic = True
        torch.backends.cudnn.benchmark = False
        os.environ["CUBLAS_WORKSPACE_CONFIG"] = ":4096:8"

Lightning ships lightning.pytorch.seed_everything(seed, workers=True). Use workers=True — without it, num_workers > 0 reintroduces non-determinism. deterministic=True slows training 10–30%; reserve it for final experiments.

Lock the environment

  • uv.lock committed to the repo, restored with uv sync.
  • Pin CUDA + PyTorch + driver combinations explicitly in the README — silent reproducibility killers.

Snapshot the config next to the checkpoint

Hydra does this for free in outputs/<date>/<time>/.hydra/config.yaml. Lightning checkpoints embed hyperparameters via self.save_hyperparameters(). Use both:

logs/runs/2026-05-10_14-32-11/ ├── .hydra/ │ ├── config.yaml # full resolved config │ ├── overrides.yaml # CLI overrides │ └── hydra.yaml ├── checkpoints/ │ └── epoch=42-val_loss=0.17.ckpt └── wandb/ └── run-20260510_143211-abc123/

Always log the git SHA

import subprocess, wandb
git_sha = subprocess.check_output(
    ["git", "rev-parse", "--short", "HEAD"]
).decode().strip()
wandb.config["git_sha"] = git_sha

Combined with the policy in your repo's CLAUDE.md (record the code/ commit SHA in the writing repo), this closes the reproducibility loop between thesis text and code.

12. RL & world-model specifics

This is the section most ML templates ignore — and it's exactly where your DreamerV3 work lives.

src/ ├── agent/ │ ├── world_model.py # RSSM: encoder → posterior → prior → decoder/reward │ ├── actor_critic.py # policy head + value head │ ├── dreamer.py # ties WM + AC + imagination rollout │ └── losses.py # KL balancing, free bits, λ-returns ├── envs/ │ ├── hm3d.py # Habitat-sim wrapper → gym-style interface │ ├── wrappers.py # frame stack, reward shaping, action repeat │ └── vec_env.py # parallel environments ├── replay/ │ ├── buffer.py # episodic; sample sequences not transitions │ └── prioritized.py # optional ├── training/ │ ├── loop.py # collect → train → imagine → update │ └── distributed.py # actor/learner split if needed └── eval/ ├── rollout.py # deterministic eval episodes └── video.py # save trajectory videos for the thesis

Replay buffers — the sneaky complexity

Dreamer-style world models sample contiguous sequences of length L (typically 16–64), not i.i.d. transitions. The standard DataLoader model breaks:

class SequenceReplay:
    def __init__(self, capacity: int, seq_len: int):
        self.episodes: list[Episode] = []
        self.seq_len = seq_len

    def add(self, episode: Episode): ...

    def sample(self, batch_size: int) -> dict[str, torch.Tensor]:
        # pick batch_size episodes; random start index in each;
        # return tensors of shape (batch_size, seq_len, ...)
        ...

Wrap it in a thin iterable, not a Dataset — the buffer keeps growing as the agent collects.

The agent–environment loop

def train(cfg):
    env    = make_env(cfg.env)
    agent  = Dreamer(cfg.agent).to(cfg.device)
    replay = SequenceReplay(cfg.replay.capacity, cfg.replay.seq_len)

    obs, _ = env.reset(seed=cfg.seed)
    for step in range(cfg.total_steps):
        # 1. act
        with torch.no_grad():
            action = agent.act(obs)
        next_obs, reward, term, trunc, _ = env.step(action)
        replay.add_step(obs, action, reward, term)
        obs = env.reset()[0] if (term or trunc) else next_obs

        # 2. learn
        if step >= cfg.warmup and step % cfg.train_every == 0:
            batch = replay.sample(cfg.batch_size)
            wm_metrics = agent.train_world_model(batch)
            ac_metrics = agent.train_actor_critic(batch)
            wandb.log({**wm_metrics, **ac_metrics}, step=step)

~200 lines of explicit loop code that a thesis reader can follow beats forcing this into LightningModule.training_step with automatic_optimization=False.

14. Cheat sheet — for the thesis refactor

  1. src/ layout, regular packages, one __init__.py per directory. Boring and correct.
  2. Public API = what __init__.py re-exports. Everything else is internal (leading underscore is enough).
  3. Protocol for "anything that quacks"; ABC only when you truly need shared base behavior.
  4. @dataclass(slots=True, frozen=True) for internal state, pydantic.BaseModel at the I/O boundary.
  5. Pass dependencies as arguments. Wire them up once at the program edge. No globals.
  6. Hydra for experiment configs. One train.py; never copy-paste a training script.
  7. Registries (or Hydra _target_, not both) for swapping encoders via a single config string.
  8. Lightning for supervised perception; plain PyTorch for the DreamerV3 loop. Right call, not a smell.
  9. W&B + git SHA + Hydra config snapshot + uv.lock = reproducibility floor.
  10. uv + ruff + pyright + pytest + pre-commit — the 2025 baseline, all configured in one pyproject.toml.
