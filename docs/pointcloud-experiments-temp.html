How the Point Cloud becomes the readout input

The aggregation happens before the agent readout. The VGGT Point Head produces a dense 518x518x3 Point Cloud. The wrapper then averages each native 14x14 patch cell, giving 37x37x3. Only after that do we flatten and append the 9D camera pose. The readout choice is the last step: linear readout or 3-layer MLP over the same 4116-dimensional WP+CP vector.

Aggregation

Each output cell is the mean of the dense Point Cloud values inside one 14x14 VGGT patch cell.

Representation

The agent does not receive the dense map in the main WP+CP path; it receives 37x37x3 + 9.

Readout

Linear and MLP variants use the same aggregated input. The difference is only how the 4116-D vector is projected.

Replay-buffer memory: why dense Point Clouds become a systems problem

The model-side question and the replay-side question are coupled. A pooled 37x37 WP+CP observation is small enough for the usual large Dreamer replay capacity. Keeping the dense 518x518x3 Point Cloud, or full VGGT token sequences, changes the storage scale by roughly two orders of magnitude per transition.

Observation storage per replay transition

37x37 WP+CP
~16 KiB fp32
64x64 WP+CP
~48 KiB fp32
Dense WP map
~1.5 MiB fp16
Full agg tokens
~2.7 MiB fp16

Numbers are observation payload only, before actions, rewards, dones, Python/Numpy overhead, sampled batches, and model activations. For dense maps, fp32 would double the dense WP number to about 3.1 MiB per transition.

Capacity implication

How the table is computed bytes/transition = element_count * bytes_per_element GiB at 1M = bytes/transition * 1,000,000 / 1024^3
37x37 WP+CP: (37*37*3 + 9) * 4 B = 16.1 KiB -> ~15 GiB at 1M.
Dense WP fp16: 518*518*3 * 2 B = 1.54 MiB -> ~1.5 TiB at 1M.
Where this memory lives The current training replay is an in-process Numpy ring buffer: observations, actions, rewards, and done flags are preallocated in host RAM. Checkpoints save the agent state, not the replay contents. Disk-backed replay would need a different implementation, for example a memmap/offline feature cache.
Representation At 1M transitions Practical config
37x37 WP+CP flat ~15 GiB 1M feasible
64x64 WP+CP flat ~46 GiB 1M borderline but possible
Dense 518x518 WP ~1.5 TiB fp16 5k cap in current configs
Full aggregator tokens ~2.6 TiB fp16 5k cap / smaller batches
Why it matters

Capacity is part of the ablation

Dense/full-token variants cannot simply keep the same replay capacity as the 37x37 run. Reducing the buffer changes the training distribution and makes the result less directly comparable.

What changes

Need a representation-aware replay

For large 3D observations the replay has to store fields with explicit dtypes such as float16, use smaller capacity, or keep only compact inputs and reconstruct/cache expensive VGGT features outside the standard flat observation buffer.

Meeting phrasing

Engineering caveat

The early dense Point Cloud runs are not only model-readout tests; they also stress replay memory. The cleaner current claim is that pooled 37x37 keeps the 3D signal while staying compatible with a large replay buffer.

eVGGT: how it differs from normal VGGT

eVGGT is not just "VGGT with fewer layers switched off". The paper Improving Robotic Manipulation with Efficient Geometry-Aware Vision Encoder proposes a distilled student model: VGGT remains the geometry teacher, while eVGGT is trained to preserve geometry-aware features with a much smaller backbone.

Normal VGGT teacher

Large geometry foundation model used to predict camera pose, depth, and dense Point Cloud outputs.

global attention frame-wise attention
embedding width1024
24 transformer blocks embed dim 1024 DINOv2-ViT-L teacher outputs: CP / depth / Point Cloud
→
knowledge distillation

Student is trained against VGGT outputs, not by simply truncating the checkpoint.

eVGGT student

Smaller geometry-aware encoder intended for robotics where online inference cost matters.

global attention frame-wise attention
embedding width384
4 transformer blocks embed dim 384 DINOv2-ViT-S reported: ~9x faster / ~5x smaller
Paper motivation

VGGT gives useful 3D reasoning, but the original model is too expensive for many real-time robotics settings.

Architecture change

The key visual differences are depth and width: 24 -> 4 VGGT transformer blocks, each with global and frame-wise attention, plus 1024 -> 384 embedding width.

Important distinction

The "4" here means transformer blocks. It is not the same as the normal VGGT Camera Head's 4 pose-refinement iterations.

Our L1 run

The current eVGGT WP+CP run still feeds Dreamer the same 37x37x3 + 9 = 4116 vector; only the upstream geometry encoder changes.

Interpretation for the landing page

Observation 1

37x37 is not arbitrary

It is the native VGGT patch grid: 518 / 14 = 37. The dense Point Cloud is pooled to that grid before the Dreamer encoder.

Observation 2

Readout depth matters

The same WP+CP input is stronger with a 3-layer MLP than with the older linear readout in the current snapshot.

Observation 3

More resolution is not yet better

The 64x64 and dense paths did not produce clean comparable runs. Present them as engineering probes, not as final negative results.
