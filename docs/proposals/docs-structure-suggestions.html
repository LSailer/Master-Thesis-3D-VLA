Docs Restructuring · 2026-05-17

Five suggestions for a tidier docs/

Today docs/ mixes 13 HTML reports, 6 Markdown plans, slide decks, ADRs and a parallel wiki at one flat level — with no landing page, no shared style, and no naming convention that tells you whether a file is a snapshot, a plan, or a deck. Five concrete moves, ordered cheapest first.

Valid as of: 2026-05-17 · branch main · HEAD 2314ad8.

SUG 1 Effort · 15 min

Rename index.html → a real docs landing page

docs/index.html is not an index. It's a slide deck titled “Supervisor Meeting · Mar 3, 2026.” A new reader who opens docs/ in a browser sees a presentation and has no map to the other 18 files.

Concrete move

git mv docs/index.html               docs/slides/2026-03-03-supervisor.html
# (or .../slides/supervisor-2026-03-03.html)

# Then write a new, lightweight docs/index.html that simply lists
# every other doc grouped by kind (reports / proposals / research / slides / plans).
Why A real index is the cheapest piece of navigation infrastructure you can add. It also gives you a single page to link from CLAUDE.md or the repo README, instead of pointing readers at “the docs folder, sort by date.”
How to apply The new landing page can be 100 lines of static HTML — one <ul> per section, one <li> per doc with a one-line description. Treat it as the README for the docs folder.

Right now, docs/index.html ranks #1 on ls docs/ alphabetically — readers expect it to be an index.

SUG 2 Effort · 30 min

Subdivide by kind, not by topic

There are already four subfolders (adr/, agents/, notes/, wiki/) but HTML reports landed flat alongside them. The rule that's emerging is “notes go in folders, HTML stays flat” — which scales badly. Move every doc into a kind-named subdir so the folder name answers “what kind of thing is this?” before you open it.

Target tree

docs/
  index.html               # SUG 1
  README.md                # SUG 5 — the “HTML vs MD” rule
  _assets/                 # SUG 4 — shared stylesheet, images
  reports/                 # point-in-time experiment reports (baseline-*.html, curriculum-scaling.html, l1-baseline-*.html)
  research/                # surveys, deep dives (dreamer-vector-input-research.html, transformer-encoder-survey.html, dreamerv3.html, dreamernav.html)
  proposals/               # design memos with suggestions (aggregator-mlp-upgrade-suggestions.html, ddd-refactor-suggestions.html, overfit-one-batch-aggregator-mlp.html)
  onboarding/              # onboarding-mlp-encoder.html and future per-variant onboarding docs
  plans/                   # baseline-training-plan.md, curriculum-preprocessing-plan.md, dreamerv3-evaluation-plan.md, slurm-ci-pipeline.md
  slides/                  # 2026-03-03-supervisor.html and future decks
  adr/                     # already exists, leave alone
  notes/                   # already exists, leave alone (meeting notes)
  agents/                  # already exists, leave alone (agent runbooks)
  wiki/                    # already exists, leave alone
Why Five new readers will all ask the same question first — “is this a proposal I should act on, or a snapshot of something that already happened?” The folder name should answer it. reports/ vs proposals/ is a stronger signal than any naming prefix.
How to apply Use git mv so history is preserved. Do it in one commit to avoid half-states. Update any cross-references (e.g. onboarding-mlp-encoder.html links to aggregator-mlp-upgrade-suggestions.html; those links will need a ../proposals/ prefix).
SUG 3 Effort · 10 min per doc, ongoing

Adopt a “valid-as-of” convention for snapshots

The review of these six files surfaced one recurring failure mode: line-anchored citations decay fast in an active refactor. onboarding-mlp-encoder.html already does the right thing — its footer says “Generated 2026-05-16 from branch feat/variant-1-aggregator-mlp at commit 34f8c05.” Make that pattern standard.

Two-line header template

<p class="subtitle">
  Valid as of commit <code>34f8c05</code> · 2026-05-16 · branch <code>feat/variant-1-aggregator-mlp</code>.
  For drift after this date, prefer <code>git log -- <paths></code> over this document.
</p>

Where it goes

FolderHeader required?Why
reports/YesSnapshot of a run; numbers will change.
onboarding/YesFile paths and shapes will move.
proposals/YesCode may already match the proposal (see ddd-refactor-suggestions.html).
research/OptionalIf grounded in upstream repos, an external-cite date is enough.
plans/Date in filenamePlans are short-lived — encode the date in the name.
slides/Date in filenameOne deck per meeting; date is the primary key.
Why The five recently-generated docs all carry “2026-05-16” in their body text but not in their filename. After a few weeks they become indistinguishable from each other in ls -t. A consistent header lets future-you (and PR reviewers) tell “is this still load-bearing?” without opening the file.
SUG 4 Effort · 1–2 hours one-off

Extract one shared stylesheet, retire the per-file CSS

Every new HTML report ships ~250 lines of bespoke CSS in its <head>. The aesthetic varies file-to-file (warm cream serif vs cool dark dev theme vs blue clinical theme). That's fine for an artist's portfolio; for a thesis docs corpus it makes the work feel uncurated and bloats every file by 5–10 KB of duplicated styling.

The change

docs/_assets/
  style.css            # one base stylesheet: typography, code blocks, callouts, tables, tags
  style-dark.css       # optional: dark variant for “dev tooling” docs that prefer it
  print.css            # optional: pdf-friendly variant

<!-- in every doc -->
<link rel="stylesheet" href="../_assets/style.css">

Keep the per-doc visual identity small — one accent color and any doc-specific diagram CSS — in a short <style> block. That's the 80/20 split: 90% shared, 10% bespoke.

Why Three downstream wins. (1) A new doc takes 5 minutes to author, not 30 spent picking colors. (2) Fixing a typography choice (e.g. better code-block contrast) becomes one edit instead of 13. (3) The corpus reads like one body of work, which matters for thesis presentation.
How to apply Start by copy-pasting the most legible existing stylesheet (the cream-serif theme used in aggregator-mlp-upgrade-suggestions.html and ddd-refactor-suggestions.html is consistent and readable) into _assets/style.css, then migrate one doc at a time. Don't try to unify everything in one PR.
SUG 5 Effort · 15 min

Write a one-page docs/README.md that defines the rules

Right now the rules for “when do I write Markdown vs HTML?” live nowhere — they have to be inferred. A short README codifies the conventions so the next Claude session (or collaborator) doesn't have to re-derive them.

Sketch contents

# docs/

A map of what lives here and the rules for adding to it.

## Folders
- `reports/`      Polished experiment snapshots. HTML. Always include a “valid-as-of commit” header.
- `research/`     Surveys and deep-dives grounded in upstream code or papers. HTML.
- `proposals/`    Design memos with suggestions. HTML.
- `onboarding/`   Onboarding docs for new variants / new collaborators. HTML.
- `plans/`        Short-lived plans. Markdown. Date-prefixed filename.
- `slides/`       Presentation decks. HTML. Date-prefixed filename.
- `notes/`        Meeting notes. Markdown. Date-prefixed filename.
- `adr/`          Architectural decision records. Markdown.
- `agents/`       Agent runbooks. Markdown.
- `wiki/`         Long-form wiki (separate index inside).
- `_assets/`      Shared stylesheet + images.

## HTML vs Markdown
- Use **HTML** when: the doc has diagrams, custom tables, multi-color callouts, slide-style layout, or will be
  shared as a static page.
- Use **Markdown** when: you want clean `git diff`s, the doc is short, or the audience is GitHub web UI.
- Never both for the same content — pick one and link from the other if needed.

## Adding a new HTML doc
1. Copy `_assets/_template.html` for the boilerplate header.
2. Drop into the right folder per the kind rule above.
3. Include the “valid-as-of” header.
4. Link it from `index.html`.
Why Documentation rot is usually a coordination problem, not a writing problem. A 60-line README that says “HTML goes in proposals/, plans go in plans/” resolves 90% of the “where do I put this?” decisions before they happen.
How to apply Add the README in the same commit as Suggestion 2's restructure so the rules and the layout ship together. Reference it from the root CLAUDE.md so Claude reads it when starting a new docs task.

Suggested order of attack

  1. SUG 1 & 5 first — pure additions, no moves, instantly useful.
  2. SUG 2 next — one commit, all git mv, fixes the “flat folder” problem.
  3. SUG 3 as you write each new doc — no batch migration needed; the convention spreads naturally.
  4. SUG 4 last — biggest effort, smallest correctness payoff. Worth doing eventually for the thesis-quality polish, but never blocking.
