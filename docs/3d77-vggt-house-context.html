Executive Summary

The experiment is not "VGGT features in replay". Replay stores only the downsampled RGB frame. A live InfiniteVGGT stream holds the current house-level WP/CP context and the trainer injects that context into sampled replay windows before the hybrid encoder sees them.

This tests a stronger idea than smaller replay: can persistent 3D scene memory help an RGB Dreamer policy in the one-house L1 setting?

Storage Claim

Replay entries are compact uint8 RGB tensors: (3,64,64). The old hybrid stores a flattened float32 vector containing RGB plus WP/CP.

Context Claim

The context is the current 4116-d WP/CP vector from InfiniteVGGT: 37*37*3 world points plus a 9-d camera pose.

Compute Reality

VGGT extraction still happens live during environment interaction. Smaller replay is not the same thing as removing VGGT compute.

Bounded Cache

The JAX InfiniteVGGT path keeps a padded streaming KV cache with a total budget of 200000 tokens and static per-block budgets of 8333.

How It Works

The adapter is the key change. During acting it resizes the current image to 64x64 for replay, extracts the current WP/CP context from the full 518x518 frame, and returns both pieces to the agent. During training it takes sampled RGB replay and broadcasts the latest live context across the sampled batch.

  1. Variant resolution: vggt_house_context maps to the same world-model HybridEncoder as the previous hybrid, but it builds a different adapter.
  2. Replay write: VGGTHouseContextObsAdapter.transform() stores only resized RGB as uint8 with normalize_on_sample=True.
  3. Live context: the adapter calls extractor.extract() on the full-resolution image and keeps the flattened WP/CP vector in memory as self._context.
  4. Replay augmentation: augment_replay_batch() replaces the sampled array batch with a dict containing image and house_context, where the context is broadcast over every sampled time step.
  5. Encoder input: encoder_obs_from_batch() packs the dict into the flat hybrid vector [rgb | context], so downstream R2Dreamer training stays unchanged.

Point-Cloud Readout Choice

Open design question: should house context use VGGT's pooled 37*37 world-point grid, the full dense point cloud, or a learned compressor that maps point-cloud evidence into a stable 1024-d context token?

The current vggt_house_context path uses the same WP/CP representation as the historical hybrid: 37*37*3 = 4107 world-point values plus a 9-d camera pose, for 4116 total VGGT context dimensions. The HybridEncoder then learns an MLP branch that projects this 4116-d vector to the configured 1024-d VGGT branch embedding, gated by the zero-init hybrid gate.

That is not the same as learning from the full dense DPT point map. The repo has a separate dense-WP variant, vggt_wp_dense_cnn, where the full-resolution metric XYZ map is treated like a (3,518,518) image and compressed by WPConvEncoder to 1024 dims. House context does not currently use that dense path.

Option Input How it reaches 1024 dims Main tradeoff
Current pooled WP/CP 4116-d flat vector. Hybrid MLP branch: 4116 -> hidden -> 1024, then gated. Cheap and already wired, but loses dense spatial detail before learning.
Dense WP CNN (3,518,518) metric XYZ map. Symlog + convolutional downsampling + final dense projection to 1024. Preserves spatial structure, but is heavier and still needs a house-context adapter design.
PointNet-style set encoder Sampled or full point set with XYZ, optionally confidence and age. Shared point MLP, symmetric pooling, final projection to 1024. Permutation-tolerant and compact, but weaker at local geometry unless neighborhood features are added.
Query-token cross attention Patch tokens, dense points, or cached keyframes. A small fixed set of learned queries attends to points and outputs one 1024-d context. Most flexible, but adds more moving parts and needs careful throughput measurement.

Practical next step: treat pooled WP/CP as the baseline house-context readout, then add one controlled dense-compression ablation. The cleanest first ablation is a dense-WP house-context adapter that reuses WPConvEncoder and keeps the rest of the run config unchanged.

Throughput Interpretation

The smoke proves plumbing, not production feasibility. The earlier log fps= was cumulative from startup, so it mixed Habitat startup, VGGT init, JAX compile, prefill, and steady-state work.

The trainer now logs perf/fps_interval and perf/ms_per_step_interval; those are the numbers to use for a real 2M/48h decision. The prod job 4995376 was still pending in the prior handoff, so no production throughput existed yet.

Current feasibility status: prior evidence did not prove the 2M in 48h target. The target requires 11.57 fps or at most 86.4 ms/step, measured after warmup with interval metrics.

Potential Problems

  1. Historical replay gets current context. A sampled sequence may have been collected before the agent saw part of the house, but the batch receives the latest house context. That can become a future-information leak relative to the sampled time step.
  2. Train-time and act-time context can differ. Acting only has the context accumulated up to now. Training can condition old observations on a newer context state, which may teach the world model a distribution it never sees online at that old time.
  3. It is L1-specific by construction. Persisting through episode resets is meaningful for one house and one object class. In multi-house curricula, not resetting by house identity could mix incompatible maps.
  4. Storage savings do not guarantee speed. The live extractor still runs on every environment step. Throughput is dominated by live VGGT, JAX compile/warmup, and training update load, not only replay size.
  5. The context is not learned memory. The policy receives a frozen extractor summary. If the useful signal requires task-specific memory compression, the current design may be too rigid.
  6. The VGGT branch may stay closed early. The hybrid encoder uses a zero-init learned gate for the VGGT branch. Early smoke diagnostics showed the model behaving almost entirely like the CNN branch.
  7. Attribution is confounded. Improvements could come from larger replay capacity, RGB normalization, hybrid gating, persistent context, or just variance. The thesis interpretation needs matched controls.
  8. Fresh worktrees need external links. VGGT-family jobs can fail at startup with ModuleNotFoundError: streamvggt unless scripts/slurm/hooks/link_external.sh links the external repos.
  9. The first smoke was dirty relative to current HEAD. The smoke manifest reported git_sha=3f3ffd7 and git_dirty=True; the branch later moved to d110f82 with throughput logging and docs cleanup. Re-run a short smoke before treating the current branch as verified.

Follow-Up Ideas

Make The Experiment Interpretable

  • Matched RGB control: run CNN with the same 1M replay capacity and validation disabled so storage capacity is not mistaken for context benefit.
  • Stale-context ablation: freeze the context after prefill or after the first episode to separate "house prior" from continual map growth.
  • Per-window snapshot: store a small context version id or compressed context keyframe so training can use the context that existed when the sequence was collected.
  • Reset policy sweep: compare reset-on-episode, reset-on-house-change, and never-reset to quantify whether persistence is helping or leaking.
  • Gate monitoring: track hybrid/gate, hybrid/vggt_frac, and hybrid/cnn_frac so a failed result is not mistaken for evidence against VGGT context when the branch never opened.

Make It Faster

  • Measure first: use interval throughput after at least 10k to 25k steps before changing architecture.
  • Update every K steps: run K in {2,4,8,16} and reuse the last context between extractor calls.
  • Async extraction: overlap VGGT extraction with environment stepping if the runner can keep causality and queueing simple.
  • Offline house map: precompute a static house-level VGGT context for L1 and feed it as an auxiliary input, then compare to the live-context variant.
  • Context drift logging: log context norm, standard deviation, delta from previous context, cache frame count, and cache length so stale or explosive context can be diagnosed quickly.

Recommended next gate: re-run a short smoke on current HEAD so interval throughput logging is present, then launch a longer warmup-aware run, read perf/fps_interval after compile settles, and only then decide whether to optimize extractor cadence or pivot to a static/offline house map.
