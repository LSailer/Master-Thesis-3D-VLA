TL;DR — three new findings

  1. v2's "99% of steps are −0.01" framing was wrong. The env runs in geodesic_delta mode by default (habitat.py:256–265): per-step reward is Δ(distance_to_goal) + step_penalty, plus +10 on goal arrival. The reward is dense, signed by direction of motion, and penalises moving away from the goal. So the η=3·10⁻⁴ collapse cannot be blamed on "no learning signal" — it is a feedback-loop failure during early training.
  2. The cumulative-discount weight in this fork is correct. danijar/dreamerv3, NM512/dreamerv3-torch, and r2dreamer all use a per-step cumprod(γ·cont); only nit is dividing by disc for exact magnitude parity with Hafner. Not a bug; matches both reference implementations.
  3. You should not change step_penalty / success_bonus right now. The dense shaping already fires; the encoder works at η=3·10⁻². The single highest-leverage change is observability — confirmed below as a GitHub issue draft.

1 — What does the agent's reward function actually look like?

From modules/envs/habitat.py:256–265 and modules/shared/configs.py:12–14:

def _compute_reward(self, dist: float) -> float:
    if self._cfg.reward_type == "sparse":
        bonus = self._cfg.success_bonus if dist < GOAL_RADIUS else 0.0
        return bonus + self._cfg.step_penalty

    reward = self._prev_dist - dist          # geodesic delta (DEFAULT)
    self._prev_dist = dist
    if dist < GOAL_RADIUS:
        reward += self._cfg.success_bonus    # +10 when first reaching goal
    return reward + self._cfg.step_penalty   # constant -0.01
Your questionAnswerWhere
Does the agent get rewarded for getting closer to the goal, or only at the end? Both, in default mode. Each movement step gives Δd = prev_dist − curr_dist. Plus +10 on first time entering the 0.2 m goal radius. habitat.py:260–264
Does moving away from the goal incur a penalty? Yes. If curr_dist > prev_dist then Δd < 0, contributing a negative reward. Combined with the constant −0.01 step penalty. habitat.py:260
Is the success bonus given on STOP or only mid-action? Only on movement actions. STOP only incurs step_penalty; it does not check the goal radius. The agent must walk into the goal radius using FORWARD/LEFT/RIGHT. habitat.py:201–212 (STOP) vs habitat.py:256–265
Any other reward components (collision, look-up/down, time-of-day)? None. Three components only: geodesic delta, step penalty, success bonus. —

Theoretical reward range under geodesic_delta

Repisode  =  (initial_dist − final_dist) − 0.01·T  +  10·𝟙[success]
For a 10 m start, 100-step success: R ≈ 10 + 9.8 − 1 = 18.8. For a 500-step timeout from 10 m with no progress: R ≈ 0 − 5 = −5.

2 — Continuous discount mask vs. paper's scalar S — benefits and challenges

Two distinct mechanisms in the actor loss are easy to conflate. The paper's Eq. 7 percentile rule and the per-step cumulative-discount weight are different things:

Eq. 7 (percentile S)Cumulative weight cumprod(γ·cont)
JobNormalize advantage magnitude across domainsDown-weight deep-imagination steps and zero out post-terminal steps
ShapeScalar (one number per batch, EMA-smoothed)Tensor (one number per (batch, time) cell)
Driver5th–95th percentile of Rλ across the batchdiscount γ × predicted continue probability
Where in codenetworks.py:444–466 (ReturnEMA)agent.py:500–502

Benefits of the cumulative weight

  • Handles in-window terminations correctly: when an imagined trajectory ends inside the 15-step horizon, cont→0 zeros all subsequent weights, preventing the actor from being trained on imagined post-terminal "ghost" steps.
  • Discounts unreliable far-future predictions: the WM is most accurate near the start of an imagined rollout; γt-style fade-out down-weights uncertain late-horizon gradients.
  • Matches both reference implementations: danijar/dreamerv3 and NM512/dreamerv3-torch both use it (see §3). Switching to a scalar would diverge from the references, not move closer to them.

Challenges

  • Coupling to the continue-head: if cont is mis-calibrated, the actor's gradient is silently re-weighted. Specifically, if cont collapses early (your llspyx9j run had loss/con = 1.7·10⁻⁴ — suspiciously low), the cumulative weight either saturates near 1 (no fade-out, fine) or near 0 (no gradient at all, bad). Worth logging weight.mean().
  • Hard to debug visually: the weight is a (batch × T) tensor, so a single scalar log doesn't capture mis-fitting; you'd want a heatmap.
  • Inconsistent magnitude with paper formula: r2dreamer's first-step weight is disc·cont; Hafner's is 1 (he divides the cumprod by disc). Same gradient direction, different magnitude — meaning published learning rates aren't directly transferable.

4 — The hypothesis to test (becomes a GitHub issue)

From v2: "the percentile normalizer's L = 1 floor applies to the width, not the absolute scale". With dense shaping confirmed, the failure mode for η=3·10⁻⁴ is sharper than I framed it in v2. Here is the precise mechanism:

## Context

The DreamerV3 actor loss in `modules/r2dreamer/agent.py:512-535` is paper-faithful, but
three runs show inconsistent behavior across `act_entropy`:

| run        | encoder | act_entropy | SR    | posterior_entropy | val/loss/dyn |
|------------|---------|-------------|-------|-------------------|--------------|
| er5ze5m6   | VGGT    | 3e-2        | 0.62  | 1.38              | -            |
| lhgoxh0y   | CNN     | 3e-2        | 0.72  | 0.66              | 35.2         |
| llspyx9j   | CNN     | 3e-4        | 0.07  | 0.06 (collapsed)  | 55.0         |

The Hafner paper claims `act_entropy = 3e-4` is sufficient across all domains,
*if* the percentile-based return normalizer (`S = Per95 − Per5`, clipped to ≥ 1) fires.
The collapse of `llspyx9j` suggests the normalizer is *not* firing on this env early in
training, but we have no metric to confirm.

## Hypothesis

The `max(1, S)` floor in `networks.py:444-466` clips the **width** of the return
distribution, not the absolute scale. Under dense `geodesic_delta` rewards on HM3D
ObjectNav with 4 actions:

1. Early in training, episode returns have small range → S = 1 (no compression).
2. Critic v(s) is near zero → A = (R − v)/1 has full magnitude.
3. A single positive A spike pulls all logit mass to one action.
4. With η = 3e-4, the entropy term cannot counter this.
5. Replay collects single-action trajectories → posterior collapse → WM useless.

## How to verify the hypothesis once metrics exist

Run an `act_entropy = 3e-4` repro for ~200k steps and check:

- If `actor/ret_scale` stays ≈ 1 for the first 50k steps → hypothesis confirmed.
- If `actor/advantage_std` > 0.5 in the first 10k steps → consistent with single-A-spike collapse.
- If both are true, the fix is to either (a) initialize `ReturnEMA` with `Per5 = -5,
  Per95 = +10` so `S` starts > 1, or (b) keep `act_entropy = 3e-2` permanently as the
  exploration floor (current solution).
