Why every collection episode hits max_episode_steps

3D-25 · offline buffer collection · The CNN baseline that converged on a1aqhpnk never terminates an episode early during the rollout in j6fpgmg1. Every single one of the first 78 episodes ran the full 500 steps. This document shows the evidence, names the cause, and proposes the fix.

TL;DR

The policy in step_001000000.pkl was trained on curriculum L1: one scene (fK2vEV32Lag) and one goal class (chair), 7499 train episodes. It never sees a goal-category input — the agent's act() consumes only image and is_first. What it learned is a fixed, scene-conditional chair-finding behavior.

The collection sbatch passes neither --curriculum-path nor --semantic, so the env defaults to the full HM3D train split — 80+ unseen houses crossed with 6 goal classes the policy never trained on. Habitat terminates an episode only on goal-proximity success or on the step cap, and STOP (action 0) is a no-op. With near-zero success probability per episode, the cap is the only termination path. Result: 100 % of episodes run to 500 steps.

The evidence

From output/offline-buffer-3d25/slurm-4762927.out, every log line shows exactly two new episodes per 1000 steps and current_ep_steps=0 — meaning the log is emitted right after a freshly logged reset() consumed the boundary:

collected  1000/500000 transitions (episode  2, current_ep_steps=0)
collected  2000/500000 transitions (episode  4, current_ep_steps=0)
collected  3000/500000 transitions (episode  6, current_ep_steps=0)
...
collected 38000/500000 transitions (episode 76, current_ep_steps=0)
collected 39000/500000 transitions (episode 78, current_ep_steps=0)

39 000 transitions divided by 78 episodes is exactly 500. Combine that with the cap in src/environments/habitat.py:246:

done = success > 0 or self._step_count >= self._cfg.max_episode_steps

Two boolean disjuncts can end an episode. The pattern says one of them never fires.

Implicit success rate so far: 0 / 78. No episode terminated through the success branch.

Why the policy can't recover from this mismatch

1. No goal conditioning

The agent's act() in src/r2dreamer/agent.py:290 takes {"image": (3,64,64), "is_first": bool} for the CNN encoder. There is no field for the goal category. During L1 training every episode was "find chair" so the policy never needed one — it just learned the visual pattern of chairs in fK2vEV32Lag. When the collection env asks it to find a bed in a different house, the policy is structurally incapable of representing that request.

2. Scene-specific learned behavior

One scene × one goal class for 2.4 M env steps is a degenerate setting that rewards memorizing the layout of fK2vEV32Lag. The L1 curriculum description in level1_1house_1goal.json is candid about this:

{
  "name": "level1_1house_1goal",
  "description": "Single house (fK2vEV32Lag), chair only — proves WM learns",
  "scenes": ["fK2vEV32Lag"],
  "categories": ["chair"],
  ...
}

"Proves WM learns" — i.e. it is a sanity-check curriculum, not a generalist policy. Asking it to navigate unseen houses is asking it to do something nobody trained for.

3. No way for the agent to "give up"

In standard Habitat ObjectNav, the agent calls STOP when it believes it has reached the goal; the env then checks proximity and emits success or failure. In this repo, habitat.py:220–231 redefines STOP as a no-op — the env automatically declares success the moment _is_success_distance(distance_to_goal) is true. The agent has no behavioural lever for early termination. Its only paths to done=True are:

  • Stumble within success radius of the goal object. Near-zero probability with no goal conditioning in a new house.
  • Hit max_episode_steps. Probability ~1.0 given the above.

The 500/500 pattern is just these two probabilities resolving.

The fix

Add the L1 curriculum to the collection sbatch. The arg threading already exists end-to-end — collect_offline_buffer.py:561 defines --curriculum-path, :353 forwards it to build_habitat_env, and the env consumes it. Two lines in collect_offline_buffer_3d25.sbatch:

.venv/bin/python scripts/r2dreamer/collect_offline_buffer.py \
    --checkpoint "${CNN_CHECKPOINT}" \
    --n-steps 500000 \
    --collect-seed 42 \
    --out-dir data/offline_buffer \
    --curriculum-path data/curriculum/level1_1house_1goal.json \
    --curriculum-mode train \
    --wandb-project 3d-vla-objectnav \
    --wandb-name "3d25-offline-buffer-${SLURM_JOB_ID}" \
    --wandb-tags "offline-buffer,3d-25,cnn-source,vggt-readouts" \
    --wandb-init-timeout 600 \
    --log-every 1000 \
    --wandb-log-every 1000

With this change the rollout env is restricted to the exact 7499 episodes the policy was trained on, success becomes a regularly-firing termination branch, and the buffer fills with non-degenerate trajectories. Episode lengths will become a distribution (success at 60–250 steps for solved episodes, 500 for the residual failures) instead of a delta at 500.

If you also want the policy to see semantic targets, add --semantic. The current checkpoint was trained without it (L1 sbatch doesn't pass any flag that enables it), so leaving it off keeps observation parity with training.

The decision you actually have to make

The patch above gives you an in-distribution buffer. The current sbatch silently gives you an out-of-distribution buffer with the same checkpoint. Which one does 3D-25 want?

Buffer flavourWhat's in itWhen the VGGT readout ablation wants this
In-distribution
L1 curriculum		 ~7500 episodes in fK2vEV32Lag, chair goal, mixed success/failure trajectories with non-trivial reward signal The readout has to predict something the policy is competent at — value, dynamics, planning targets. Matches the training distribution of the CNN baseline so the comparison is fair.
Out-of-distribution
full HM3D train split (current)		 ~1000 random-walk trajectories of length 500 each, near-zero reward signal, near-zero goal-reach events You want to probe whether VGGT readouts transfer to unseen visual distributions independent of policy competence. Less useful for "ablate the readout against the L1 baseline" because there is no L1 baseline behaviour to ablate.

The docstring at the top of collect_offline_buffer.py calls this "the canonical offline replay buffer for the VGGT readout ablation". Canonical-and-ablation framing strongly suggests in-distribution: the readout needs trajectories where the latent state actually carries useful structure for the downstream task. Random-walk frames from unseen houses produce noisy readout targets.

Secondary observations

Hidden-state reset is not the problem

Per-episode RSSM reset works: habitat.py:216 returns {"is_first": True, ...} from reset(), the collect loop passes that through, and agent.act() zeros _act_stoch / _act_deter / _act_prev_action when is_first is true. Confirmed at agent.py:311–314. So the policy enters each episode with a clean recurrent state — the failure is not state pollution, it is the absence of useful behaviour to begin with.

Throughput won't reach 500 000 in 12 h

Current run rate is ~5.3 transitions/sec, projecting to roughly 228 000 transitions over 12 h. Even with the curriculum fix the buffer will likely cap below the requested 500 K within the SLURM walltime. Either bump --time (the gpu_h100_il queue has higher caps) or accept a partial buffer.

The dev smoke job crashed with SIGABRT, not TIMEOUT

Job 4762909 (dev) died at 13:03 with exit 134, last Python log being the HF Hub auth warning. Mem at 20 % so it isn't host OOM — most likely a JAX-XLA abort during compile or a transient HF download failure. Prod survived past the same wall-clock point so it skated through whatever transient bit dev. Worth setting HF_TOKEN in the sbatch env to close that failure mode for future runs.
