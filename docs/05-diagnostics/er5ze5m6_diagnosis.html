Q1 — Why does the action distribution look uniform?

The W&B run logs only per-episode aggregates action/{forward,left,right,stop}_pct. There is no actor/entropy or per-batch action histogram, so we cannot directly see the policy's logit distribution. What the data does show:

The aggregate hovers around the uniform mean of 0.25. Below are five concrete prognoses, ranked by how strongly the run's numbers and the code support them.

Prognosis 1 — Entropy bonus is ~100× the paper default strong

The repo currently runs with act_entropy = 3·10⁻² (config.py:72). The DreamerV3 paper and the reference code use 3·10⁻⁴; commit 9b5f26f in this repo is even titled "fix(actor): use DreamerV3 paper default act_entropy=3e-4", which contradicts the value actually loaded by the run.

The actor objective in agent.py:532–535 is

Lπ  =  𝔼τ [ −sg(Anorm) · log π(a|s)  −  η · H[π(·|s)] ]
with η = act_entropy, Anorm = (Rλ − V) / ret_scale

An η that is 100× too large floods the gradient with an "exploration" term that pulls every state's logits toward the uniform prior. Empirically the observed loss magnitude (−0.036) is essentially the entropy term alone at η = 0.03 (see Q3 below).

Prognosis 2 — Tiny advantage signal vs. dominant entropy term strong

Reward shaping is step_penalty = −0.01, success_bonus = +10. Successful HM3D ObjectNav episodes are 30–250 steps, so the per-step return ranges roughly from −5 (failure) to +9.5 (success). After percentile-based ret_scale normalization (DreamerV3-style), Anorm on most timesteps is close to zero. With η = 0.03 dominating, the gradient from the policy-gradient term is drowned out.

Prognosis 3 — World-model KL stays large (5.95) — imagined returns are noisy moderate

loss/dyn and loss/rep both end at 5.95 (KL divergence between RSSM prior and posterior) — high for a model trained for 2.1 M steps. If the world model is poorly fit, λ-returns over imagined rollouts (imagination_horizon = 15) are essentially noise, so the advantage signal is noise, and the actor has nothing to learn from. The actor then defaults to whatever the regularizer prefers — uniform.

Prognosis 4 — Curriculum is easy enough that random walking already succeeds supporting

Tags 1house, chair-only, level1 mean a single house with chairs as the only target. The success rate climbs to 0.62 even though the action distribution remains near-uniform — i.e. the env doesn't penalize a near-random policy, so the gradient toward a peaked policy is weak by construction. This makes the entropy bonus the dominant force.

Prognosis 5 — unimix_ratio is at the paper default and is not the cause ruled out

unimix_ratio = 0.01 in the config and on line 523 of agent.py. That can pin the marginal at no worse than 0.99·π̂ + 0.01/N — i.e. it allows up to a 99% peaked policy. So unimix alone cannot explain a near-uniform distribution. (It would, however, mask a totally-collapsed actor.)

Recommended fixes, in order: (a) revert act_entropy to 3·10⁻⁴; (b) add actor/entropy and per-batch action probs to the logging in trainer.py:451 so the next run is diagnosable; (c) inspect why loss/dyn stays at 5.95 — a bad world model is the root cause that lets the entropy bonus win.

Q3 — Why is the policy loss negative? (5 pictures + the math)

The actor objective by construction is the negation of (advantage-weighted log-prob + entropy bonus):

Lπ(θ)  =  𝔼[ −Anorm · log πθ(a|s)  −  η · H[πθ(·|s)] ]
policy-gradient term (red)  +  entropy bonus, subtracted (blue)

Both terms can — and routinely do — push the loss negative.

Picture 1 — Decompose the observed loss into its two terms

Picture 2 — Loss vs. policy temperature (sharpness)

Parameterise the actor as softmax(z/T) with a single peaked logit z. As T → ∞ the policy approaches uniform; as T → 0 it becomes deterministic.

Picture 3 — Loss vs. act_entropy coefficient η

For a uniform policy, H[π] = log N = log 4 ≈ 1.386 is fixed, so the entropy contribution to the loss is linear in η:

Lmin(η)  =  −η · log N  =  −1.386 · η

Picture 4 — Why the policy-gradient term itself can be negative

Even without any entropy bonus, the term −Anorm·log π is sign-flipped: log π < 0 always. So:

  • If the actor places high probability on a high-advantage action: A > 0, log π close to 0 (small negative). Product −A·log π is small positive, contributing positively to the loss that we are minimizing — wait, that's wrong sign. Let's redo carefully.
A > 0, log π → 0⁻:  −A · log π = −(+)·(0⁻) = +small  ⇒ loss ↑
A > 0, log π = −large:  −A · log π = −(+)·(large neg) = +large  ⇒ loss ↑↑
A < 0, log π → 0⁻ (high prob bad action):  −A · log π = −(−)·(0⁻) = −small  ⇒ loss ↓

So when the good actions already have high probability (or the bad actions have low probability), the policy-gradient term itself becomes positive and small; it goes to zero only when the policy is optimal. The negative loss values you see come from the entropy bonus below the PG term — which is exactly the breakdown in Picture 1.

Picture 5 — DreamerV3 does this on purpose: the loss has no zero

Unlike supervised cross-entropy, the actor objective in REINFORCE-with-entropy is unbounded below. Hafner et al. (2023) write the actor loss as L = −sg(Rλ)/max(1,S) · log π − η · H; the entropy term is a reward shaping that keeps the policy stochastic. Reading the loss curve like a supervised loss ("approaching zero = good") is wrong — what you want is:

  • actor/entropy trending down over training (policy peaks);
  • imag/return_mean trending up;
  • actor/loss can stay slightly negative forever — its variance matters, not its sign.
Code reference (agent.py:512–535) 
adv = (ret - value) / ret_scale
logpi = (log_probs * one_hot_action).sum(-1)
entropy = -(probs * log_probs).sum(-1)
losses["policy"] = jnp.mean(
    jax.lax.stop_gradient(weight[:, :-1])
    * -(logpi * jax.lax.stop_gradient(adv) + cfg.act_entropy * entropy)
)

Q4 — Web search: is this a known DreamerV3 issue?

Findings from the official repo, the paper, and forks:

Negative actor loss is by design

danijar/dreamerv3/agent.py implements policy_loss = sg(weight) * −(logpi · sg(adv_normed) + actent · entropy_sum) — identical in shape to this repo. The DreamerV3 paper (Hafner et al. 2023, arXiv 2301.04104) gives the same formulation. A negative loss is the expected steady state, not a bug.

Uniform-actor failure mode

The most-cited root cause in danijar/dreamerv3 issues and the EclecticSheep DreamerV3 walkthrough is exactly the one this run hits: the entropy regularizer dominates a small advantage signal in sparse-reward / weakly-shaped environments. ObjectNav with step_penalty = −0.01, success_bonus = +10 is a textbook sparse-reward setting; the published DreamerV3 result on Crafter uses actent = 3·10⁻⁴ precisely to avoid this. The NM512/dreamerv3-torch README also warns that the fork's older default hyperparameters under-perform on sparse-reward tasks for the same reason.

"is_first stuck at 1" failure mode

This is a different DreamerV3 pathology than what this run shows: in danijar/dreamerv3/rssm.py, nn.mask((deter, stoch, action), ~reset) zeros the recurrent state whenever reset is true. If is_first in the replay batch were genuinely 1 every step, the RSSM would be reduced to a feed-forward encoder, the world model would never learn temporal structure, and downstream the actor would receive useless advantages. Public discussion: danijar/dreamerv3#158, Ray discuss thread. This is the failure to watch out for, but in this run it is not the diagnosis (see Q5).

Sources: danijar/dreamerv3 · NM512/dreamerv3-torch · Hafner et al. 2023 · EclecticSheep DreamerV3 · VitaLab notes · DreamerV3-XP (sparse rewards)

Q5 — Why is episode_reset "always 1"?

Short answer: it isn't logged at every step. It is hard-coded to the integer 1 inside the per-episode metrics callback, and emitted only on episode end.

episode_reset has exactly the same number of logged samples as episode/count (6 518). It is a constant marker, emitted once per episode boundary — the W&B chart shows a flat line at 1 because that is its only ever-emitted value, not because the env resets every step.

What is not wrong (verified)

  • Episode lengths vary — sampled values 31, 500, 36, 500, 210, 500, 500, 371, 88, 77, 177, 251, 283, 41, 93. Truncation at 500 is normal; episodes ≠ 1 step.
  • Replay-buffer is_first is computed correctly — replay_buffer.py:85–87: is_first[:,0] = True; is_first[:,1:] = dones[:,:-1]. So inside the WM training batches the per-step flag is the real episode boundary, not a constant 1.
  • Continue head learned a sensible thing — loss/con = 1.77·10⁻⁴ at the end (the agent rarely predicts done, which matches an env where most steps are mid-episode).

What is mildly misleading and should change

  • Rename episode_reset to episode/end_marker (it's not a reset signal — it's a "this row is the end of an episode" indicator).
  • If you actually want to track whether the RSSM is being reset correctly inside training batches, log replay/is_first_rate = is_first.mean() per WM step. Expected value ≈ 1 / mean_episode_len → a few %.
  • If a W&B panel is showing this metric as "always 1 across the entire run", that's just step-fill on a sparse series — not a runtime issue.
Verdict: not a bug. The metric is sparse, hard-coded, and only ever emitted at episode end. The label is just confusing.

Combined recommendation

  1. Fix the entropy coefficient. Set act_entropy = 3·10⁻⁴ in config.py:72 — the commit message 9b5f26f claims this is already done; verify the value the run actually loaded.
  2. Add the missing actor & world-model metrics from Q2 — without actor/entropy, advantage stats, and a per-batch is_first_rate, the next run will be just as undiagnosable.
  3. Diagnose the world model — loss/dyn = loss/rep = 5.95 after 2.1 M steps is high; if these are also literally identical numbers (not just rounded the same), check whether the two losses share a buffer/update.
  4. Rename episode_reset to something like episode/end_marker and add a real per-step is_first_rate.
