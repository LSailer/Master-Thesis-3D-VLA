Making VGGT aggregator-token replay feasible for 2M ObjectNav steps

The current full-token Transformer implementation is functionally correct, but the 2M-step target is blocked by throughput. This report compares feasible design directions and recommends the smallest next bwUniCluster experiment.

Recommendation

Do not continue with full (1374,1024) replay for production. The next experiment should be a deterministic adapter-side patch-grid pooling variant, starting with 8x8 pooled patch tokens plus camera/register tokens: 69 x 1024 fp16 values per transition. Profile it with train_ratio=4 and train_ratio=8 before any long run.

The 48h SLURM target gives 86.4 ms/env step. The current online VGGT + non-training overhead already costs about 67.6 ms/env step, leaving roughly 18.8 ms for replay sampling and training. Full-token replay cannot fit that budget.

The smallest useful next implementation is not a new large architecture. It is a throughput probe: preserve token structure at a coarser spatial grid, keep VGGT frozen/headless, and measure whether a compact token sequence can cross the 11.57 env steps/sec threshold required for 2M steps in 48h.

Fairness note: the current train_ratio=32, batch_size=1, seq_len=8 setup is not an apples-to-apples learning comparison against the default R2Dreamer configuration (train_ratio=512, batch_size=16, seq_len=64) or the other VGGT variants (train_ratio=128, batch_size=4, seq_len=32). It is a reduced feasibility probe. A follow-up H100 smoke with the VGGT-like schedule B=4,T=32,train_ratio=128 did not reach steady profiling: the first train step failed with GPU OOM while trying to allocate 39.54 GiB. The global default B=16,T=64 case would be larger again, so it was not a useful next run for the full-token design.

Why baseline parameters run out of memory

The per-update memory driver is B*T, not train_ratio by itself. train_ratio controls how often updates run per environment step: updates/env = train_ratio / (B*T). The memory needed by one update is set by the sampled replay batch shape. With full VGGT aggregator tokens, one update feeds (B*T, 1374, 1024) into the trainable encoder, then the encoder projects to 256 channels and runs 8-head self-attention over all 1374 tokens.

Replay input values      = B * T * 1374 * 1024
Replay input fp16 bytes  = values * 2
Encoder input fp32 bytes = values * 4
Attention matrix values  = B * T * heads * 1374 * 1374
One fp32 attention matrix = attention_values * 4

This table is a lower-bound style explanation. Real JAX/XLA training needs more than one attention matrix: logits, softmax/probabilities, Q/K/V projections, MLP activations, residuals, gradients, optimizer temporaries, and compiler workspaces can coexist. That is why the B=4,T=32 theoretical single-matrix number is 7.20 GiB, while the actual failed allocation was 39.54 GiB. The default B=16,T=64 setting is therefore not just slow; it is structurally too large for full 1374-token attention on one H100.

Why FP16 Replay Still Hurts

The replay buffer stores fp16, but sampling converts to fp32 JAX arrays. In the current code, sampled NumPy observations are gathered and then packed with jnp.array(obs_b, dtype=jnp.float32). JAX's device transfer API returns an array resident on device when data is moved there, so the sampled batch becomes a host-to-device transfer burden during training.

Full fp16 storage helps storage capacity, but it does not solve the training input-pipeline problem because the learner consumes fp32 batches and repeats that transfer for every train update.

Official DreamerV3 dtype comparison

I checked the official external danijar/dreamerv3 checkout cloned at external/dreamerv3, commit e3f0224. The important difference is that DreamerV3 replay does not store large precomputed floating-point vision-token tensors. It stores raw transition fields in their native dtype, then casts inside the JAX model according to the configured compute dtype.

Code pathObserved dtype behaviorRelevance for 3D-75
embodied/core/chunk.py Replay chunks allocate arrays with the dtype of the first inserted step: np.empty((size, *v.shape), v.dtype), and save with np.savez_compressed. Official replay preserves storage dtype; it does not force all replay data to fp16 or fp32.
embodied/core/replay.py Replay.add() converts fields with np.asarray(v) and keeps that dtype. The replay system is dtype-preserving. The payload size is determined by what the environment/agent inserts.
dreamerv3/main.py / embodied/core/wrappers.py Environment wrapping normalizes dtypes before insertion: images remain uint8, floats become float32, integers become int32, and flags remain boolean. DreamerV3 keeps compact image observations in replay instead of storing already-expanded feature tensors.
dreamerv3/configs.yaml Default JAX compute dtype is bfloat16. Compute precision is separate from replay storage precision.
dreamerv3/rssm.py Image observations are asserted to be uint8, then encoded via nn.cast(..., force=True) / 255 - 0.5. Official DreamerV3 stores compact image replay and only casts on the learner side.
embodied/jax/nets.py nn.cast() casts floating tensors to COMPUTE_DTYPE, normally bfloat16. A closer DreamerV3-style design for 3D-75 would avoid sampling full tokens as fp32 NumPy-to-JAX batches and cast inside the encoder to bf16/fp32 only where needed.
embodied/jax/agent.py The learner stream does not globally cast every batch field to fp32 before device transfer; model code casts at use sites. This differs from the current 3D-75 replay path, where ReplayBuffer.sample() packs obs as jnp.float32 immediately.

Bottom line: official DreamerV3's efficient replay story comes mostly from storing compact raw observations such as uint8 images, not from storing huge feature tensors in fp16. For 3D-75, fp16 token storage is still much larger than DreamerV3 image replay, and the current sample path immediately turns those tokens into fp32 JAX arrays. Matching DreamerV3 more closely would mean compact pre-replay representations plus delayed/mixed-precision casting inside the model, not just changing the replay array dtype.

Extractor-Side Speed Track

The paper Improving Robotic Manipulation with Efficient Geometry-Aware Vision Encoder is directly relevant for the online VGGT cost. It proposes eVGGT, a distilled student that keeps geometry-aware latent features but reduces the model. The local JAX VGGT port currently uses depth=24, embed_dim=1024, and num_heads=16 in the aggregator, and the DINOv2 patch embed is also fixed to depth=24. Therefore, reducing blocks or width is not just a command-line switch in the current code; it requires either a compatible distilled checkpoint or a new weight-transfer/training path.

Can we change the blocks without training? Only as a speed ablation. The external andvg3/eVGGT code does not simply drop VGGT layers and keep the original weights. Its policy encoder builds VGGT_LDM with embed_dim=384, depth=4, num_heads=4, mlp_ratio=2.0, num_register_tokens=2, and a smaller dinov2_vits14_reg patch embed, then loads separate distillation weights and freezes the model. A no-training truncation of our 24-block, 1024-wide VGGT would change the feature distribution and should not be treated as a valid eVGGT-equivalent production encoder without quality validation.

Can reduced VGGT be combined with StreamVGGT? In principle yes: streaming is an inference schedule and cache, while eVGGT is a smaller/distilled model. But the current R2Dreamer path is a JAX port of the StreamVGGT-shaped model, not an eVGGT port. It instantiates the default Aggregator(), loads the lch01/StreamVGGT checkpoint, creates caches of length depth=24, uses static budgets tuple([8333] * 24), and exposes 1374 x 1024 final global tokens. A reduced eVGGT-style model would need a matching StreamVGGT/eVGGT implementation: new weights, new weight transfer or PyTorch bridge, cache depth 4, width 384, heads 4, register count 2, and updated replay/adapter shapes. So this is a plausible follow-up track, but not a drop-in switch for the current 3D-75 branch.

Takeaway: eVGGT-style block and width reduction is worth a follow-up issue for the online extractor bottleneck. For the immediate 3D-75 feasibility question, it should be combined with token-count reduction. The current bottleneck has two separate parts: 54.13 ms/env online VGGT extraction and replay/training over 1374 tokens. Reducing extractor depth helps the first part; pooling or selecting tokens before replay is still needed for the second part.

Cluster vs Local

Use local/Codex for: design review, web/paper search, HTML annotation, CPU shape tests, and static report generation.

Use bwUniCluster/H100 for: any claim about VGGT extraction, JAX/XLA compilation, host-to-device transfer, and ObjectNav step throughput. A local machine without GPU cannot represent the bottleneck measured here.
