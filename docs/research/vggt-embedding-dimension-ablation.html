Experiment prototype · VGGT token compression

What happens when VGGT token embeddings shrink to 512 or 256 dimensions?

This page frames a standalone dimension-ablation experiment for the VGGT/VTC geometry encoder. It focuses only on direct geometry quality so the experiment can measure how much depth, point, pose, and token quality changes when embeddings shrink.

01 · Research question

Compression is not just a storage trick

Motivation

Paper connection

The robotics paper compresses VGGT into eVGGT by reducing the Transformer depth from 24 blocks to 4 blocks and using a smaller visual backbone. That makes the encoder deployable, but it raises the same core question for this thesis: how much geometry survives compression?

This ablation

Width reduction

Instead of changing only block count, this experiment changes token embedding width. The raw aggregator token is 1024-D; the candidates compress it to 512-D or 256-D before the token Transformer consumes it.

Main risk

Geometry bottleneck

If the width is too small, the encoder may keep coarse scene layout but lose object boundaries, camera-pose cues, depth precision, or local 3D structure.

Hypothesis: 512-D may be a useful middle ground: large enough to preserve most geometry cues while cutting encoder compute. 256-D is the stress test: it should expose whether VGGT's geometry signal needs high-dimensional token channels or is mostly low-rank.

Footprint

VTC width controls feature size

The intended experiment is not PCA. We change the VTC / token-encoder parameterization so its token width is d_model = 512 or 256, then evaluate the geometry outputs directly. The question is how much quality is lost when the encoder itself has fewer embedding channels.

Compute

Smaller VTC reduces compute

Reducing d_model shrinks QKV projections and MLP layers in the Token Transformer. Token count stays 1374, so the attention matrix has the same spatial size, but each token carries fewer channels.

04 · Quality risks

What quality difference should we expect?

512-D

Likely retains global geometry and many semantic cues if the VTC can use the smaller channel budget. Risk is moderate: smaller head dimensions can weaken fine object boundaries, depth edges, and small-object 3D structure.

256-D

Strong bottleneck. Useful as a stress test for whether VGGT tokens are highly redundant. Expect cheaper inference, but more risk of noisy depth, poorer point-map consistency, and worse camera-pose estimates.

4 blocks

The paper's 4-block student reduces depth, not just width. Combining 4 blocks with 512/256-D tokens compounds compression: if performance drops, separate whether the cause is shallower geometry reasoning or narrower token bandwidth.

Important implementation note: 512 and 256 are clean Transformer widths because both divide evenly across common attention head counts. With 8 heads, they give 64 and 32 dims/head.

07 · Metrics and decision rule

Measure geometry quality only

Depth / points

Does 3D reconstruction survive?

Track depth AbsRel, delta accuracy, point-map L1/L2 error, Chamfer distance when ground-truth points are available, and edge/detail degradation.

Camera pose

Does pose geometry survive?

Track relative pose translation/rotation error and pose consistency across adjacent frames or multi-view image groups.

Token fidelity

What did width reduction remove?

Compare token cosine similarity to the 1024-D reference, attention maps over the 37x37 patch grid, and nearest-neighbor scene consistency.

Decision rule: keep a reduced dimension only if it cuts encoder footprint/compute substantially while staying close to the 1024-D VGGT reference on direct geometry metrics. If 256-D matches 1024-D, the original token width is probably overkill for geometry reconstruction; if only 1024-D works, VGGT's geometric reasoning depends on high-bandwidth token channels.
