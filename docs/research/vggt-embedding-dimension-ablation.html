Experiment prototype · VGGT token compression

What happens when VGGT token embeddings shrink to 512 or 256 dimensions?

This page frames a dimension-ablation experiment for the token-preserving VGGT encoder. It separates storage, compute, and quality effects so the experiment can test whether smaller token embeddings keep enough geometry for R2Dreamer.

01 · Research question

Compression is not just a storage trick

Motivation

Paper connection

The robotics paper compresses VGGT into eVGGT by reducing the Transformer depth from 24 blocks to 4 blocks and using a smaller visual backbone. That makes the encoder deployable, but it raises the same core question for this thesis: how much geometry survives compression?

This ablation

Width reduction

Instead of changing only block count, this experiment changes token embedding width. The raw aggregator token is 1024-D; the candidates compress it to 512-D or 256-D before the token Transformer consumes it.

Main risk

Geometry bottleneck

If the width is too small, the encoder may keep coarse scene layout but lose object boundaries, navigational affordances, or pose-sensitive details needed by the RSSM.

Hypothesis: 512-D may be a useful middle ground: large enough to preserve most geometry cues while cutting storage and Transformer compute. 256-D is the stress test: it should expose whether the policy needs high-dimensional VGGT semantics or mostly low-rank geometry.

Storage

VTC width controls stored features

The intended experiment is not PCA. We change the VTC / token-encoder parameterization so its token width is d_model = 512 or 256, then store and train on those smaller embeddings. The question is how much quality is lost when the model itself has fewer embedding channels.

Compute

Smaller VTC reduces compute

Reducing d_model shrinks QKV projections and MLP layers in the Token Transformer. Token count stays 1374, so the attention matrix has the same spatial size, but each token carries fewer channels.

04 · Quality risks

What quality difference should we expect?

512-D

Likely retains global geometry and many semantic cues if the VTC can learn to use the smaller channel budget. Risk is moderate: smaller head dimensions can weaken fine object boundaries, but R2Dreamer may only need stable layout and navigability cues.

256-D

Strong bottleneck. Useful as a stress test for whether VGGT tokens are highly redundant. Expect faster/cheaper training, but more risk of lower reward prediction quality, worse RSSM posterior stability, and degraded ObjectNav behavior.

4 blocks

The paper's 4-block student reduces depth, not just width. Combining 4 blocks with 512/256-D tokens compounds compression: if performance drops, separate whether the cause is shallower geometry reasoning or narrower token bandwidth.

Important implementation note: 512 and 256 are clean Transformer widths because both divide evenly across common attention head counts. With 8 heads, they give 64 and 32 dims/head.

06 · Metrics and decision rule

Measure policy quality and representation quality separately

World model

Does the RSSM still model the task?

Track reward MSE/twohot loss, continue loss, representation KL, posterior entropy, and heldout k-step rollout error.

Policy

Does navigation behavior survive?

Compare success rate, SPL/SoftSPL, collision rate, path length ratio, and sample efficiency at matched environment steps.

Geometry proxy

What did compression remove?

Probe linear depth/world-point reconstruction from frozen tokens, nearest-neighbor scene consistency, and attention maps over the 37x37 patch grid.

Decision rule: keep a reduced dimension only if it cuts memory/compute substantially while staying within a small tolerance of the 1024-D baseline on heldout world-model probes and downstream ObjectNav metrics. If 256-D matches 1024-D, the original token width is probably overkill for this task; if only 1024-D works, the policy depends on high-bandwidth VGGT semantics.
