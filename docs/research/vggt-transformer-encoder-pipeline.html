Design proposal · R2Dreamer / VGGT

Token-preserving Transformer Encoder over VGGT geometry embeddings

The current code can consume VGGT as flat world-points, pooled aggregator vectors, raw flattened tokens, or RGB+VGGT hybrids. This design adds a middle path: keep the VGGT patch tokens structured, run a small Transformer encoder on them, then feed a compact geometry-aware embedding into the existing Dreamer world model.

01 · Paper signal

What to borrow from eVGGT

Geometry latent

Use the latent, not the point cloud

Vuong, Vu, and Reid integrate eVGGT by removing the prediction heads and passing the frozen geometry-aware latent into ACT and Diffusion Policy. Their comparison suggests the implicit latent is more useful than unstructured point clouds for manipulation policies.

Efficiency

Keep the student path small

The paper compresses VGGT by reducing transformer blocks and using a smaller DINO backbone, reporting a much faster and smaller geometry encoder. For this thesis code, that argues against a huge Dense layer over 1.4M flattened tokens.

Policy handoff

Adapt to the policy interface

eVGGT is inserted by adapting latent geometry features to the downstream policy dimension. In R2Dreamer, the matching interface is the encoder output consumed by R2RSSM.observe().

Design translation: instead of predicting VGGT heads, expose aggregator_features, preserve the 37x37 patch token grid, add a lightweight Transformer encoder, and project the resulting readout to vggt_embed_dim.

03 · Proposed pipeline

Where the Transformer Encoder sits

Click each stage to inspect the shape contract. The new block sits after VGGT aggregation and before the RSSM. VGGT remains frozen and headless for the token variant.

Shape convention: 1374 is the number of VGGT tokens, while 1024 is the feature width of each token. The aggregator output is (1374, 1024): 1 camera + 4 register + 1369 patch tokens, each with a 1024-D embedding. Register tokens are learned non-spatial scratch tokens: they give attention somewhere to store global context / absorb nuisance information without forcing every artifact into patch tokens. The current downstream token layout drops them because it focuses on the camera summary plus spatial patch grid, leaving (1370, 1024). For a Token Transformer, they are cheap enough to ablate: keeping them gives (1374, 1024), only 0.29% more tokens/storage. My recommendation is to include a thesis ablation keep registers vs drop registers, not assume either is correct.

512-D option: if we project each token from 1024 → 512 before storing replay, the layout becomes (1370, 512) and storage halves to 1.40 MB per transition (140.3 GB for 100,000 slots). If the projection is inside the trainable Token Transformer, replay still stores (1370, 1024); only the Transformer compute after projection is reduced.

How the Token Transformer learns: it is not trained by a separate VGGT loss. VGGT is frozen, but the Token Transformer is the trainable R2Dreamer encoder, stored under params["encoder"]. During train_step(), replay tokens pass through encoder → RSSM.observe(); then jax.grad(total_loss) updates the Token Transformer.

The useful gradient comes from the world-model and representation objectives: representation KL, reward prediction, continue prediction, Barlow/rep-value through the RSSM feature, and optional decoder loss for RGB-capable variants. The actor/critic behavior loss mostly trains policy/value heads because imagined rollouts start from detached latent states.

Replay buffer

Save the adapter output: flattened raw VGGT tokens [camera token | 37x37 patch tokens] with shape (1370 * 1024,), stored as float16 per frame. Do not save the Transformer output; it is recomputed by the trainable agent encoder from sampled replay batches.

Per transition 1,402,880 values * 2 bytes/value = 2.81 MB / 2.68 MiB. The factor 2 is because float16 is 16 bits = 2 bytes.
Capacity implication 100,000 slots would be 280.6 GB / 261.3 GiB for features only, so raw-token replay is not practical at normal Dreamer buffer sizes.

04 · Encoder architecture

Small token encoder, not a giant flattened MLP

Recommended first variant

Standalone token Transformer

Input: (B, 1370, 1024) after reshape. Use the camera token as a global scene token and patch tokens as spatial geometry evidence.

Blocks: RMSNorm → MultiHeadDotProductAttention → residual → MLP → residual, with 2 layers, 8 heads, MLP ratio 2.

Readout: concatenate camera token output and mean-pooled patch output, then Dense(1024).

Optional second variant

Hybrid RGB + token Transformer

Reuse the existing HybridAggRawEncoder split, but replace its raw-token MLP branch with the Transformer encoder and keep the zero-init scalar gate.

This preserves the known-safe start condition: training begins as CNN-Dreamer, then learns how much geometry to admit. 

class VGGTAggTokenTransformerEncoder(nn.Module):
    embed_dim: int = 1024
    token_dim: int = 1024
    num_tokens: int = 1370
    depth: int = 2
    heads: int = 8
    mlp_ratio: int = 2

    def __call__(self, obs):
        # obs: (B, 1370 * 1024) from replay
        x = obs.astype(jnp.float32).reshape(obs.shape[0], self.num_tokens, self.token_dim)
        cam = x[:, :1]
        patches = x[:, 1:]
        patches = patches + learned_2d_pos_embed(37, 37, self.token_dim)
        x = jnp.concatenate([cam, patches], axis=1)
        x = transformer_blocks(x, depth=self.depth, heads=self.heads)
        readout = jnp.concatenate([x[:, 0], x[:, 1:].mean(axis=1)], axis=-1)
        return nn.Dense(self.embed_dim, name="proj")(RMSNorm()(readout))

06 · Experiment plan

Compare against the existing VGGT baselines

Ablation A

vggt_aggregator_mlp

Current pooled-token baseline: camera, mean patch, max patch. Fast and compact, but loses spatial token relations.

Ablation B

vggt_agg_raw_mlp

Current raw-token baseline. Preserves information in replay but destroys token structure through flattening and a huge first Dense.

Ablation C

vggt_agg_token_transformer

New design. Preserves the token grid, uses localizable geometry context, and keeps parameter count controlled.

Acceptance metric: the token Transformer is justified if it improves ObjectNav learning or heldout world-model probes over pooled aggregator features without approaching the memory and compile cost of the raw flattened MLP path.
